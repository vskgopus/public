      Module 1 — Embedded C Basics

      ← Course home · Next: MCU & Peripherals → · Take the quiz

      Learning goals

      • Choose correct fixed-width data types and understand integer promotion.
      • Set, clear, toggle and test bits in registers safely.
      • Explain what volatile, const and static do on an embedded target.
      • Describe how a C program is laid out in Flash and RAM.
      • Expert: apply MISRA C, avoid integer, aliasing and concurrency traps, bound stack and time, and write code that survives certification review.

      Beginner 1. Beginner

      1.1 Use fixed-width types

      The C standard only gives minimum sizes for char, short, int and long. int is 16 bits on some 8/16-bit MCUs and 32 bits on ARM Cortex-M. When the size matters (registers, protocols, file formats), include <stdint.h>:

      Type Width Range
      uint8_t / int8_t 8 bits 0…255 / −128…127
      uint16_t / int16_t 16 bits 0…65 535 / −32 768…32 767
      uint32_t / int32_t 32 bits 0…4 294 967 295 / −2 147 483 648…2 147 483 647

      <stdbool.h> gives you bool, true and false.

      1.2 Bit manipulation

      Peripheral registers are controlled bit by bit. Learn these four forms by heart:

      #define LED_PIN 5U

reg |=  (1U << LED_PIN);   /* set bit 5    */
reg &= ~(1U << LED_PIN);   /* clear bit 5  */
reg ^=  (1U << LED_PIN);   /* toggle bit 5 */
if (reg & (1U << LED_PIN)) { /* bit 5 is 1 */ }

      Use the U suffix. In 1 << 31 the 1 is a signed int, and on a 32-bit int shifting a 1 into the sign bit is undefined behaviour. 1U << 31 is well defined.

      To write a multi-bit field (for example bits 4–6), clear the field first, then OR in the new value:

      #define MODE_POS   4U
#define MODE_MASK  (0x7U << MODE_POS)

reg = (reg & ~MODE_MASK) | ((mode << MODE_POS) & MODE_MASK);

      1.3 Hexadecimal and binary

      Registers are written in hex because each hex digit maps to exactly 4 bits: 0xA5 = 1010 0101. Practise converting both ways until it is automatic.

      Intermediate 2. Intermediate

      2.1 volatile

      volatile tells the compiler that a variable can change outside the normal flow of the program, so every read and write in the source must really happen. Without it, the optimiser may keep the value in a CPU register or delete a loop that seems to do nothing.

      Use volatile for:

      1. Memory-mapped hardware registers.
      2. Variables shared between an interrupt service routine (ISR) and main code.
      3. Variables shared between RTOS tasks (together with proper locking).
      volatile bool data_ready = false;

void UART_IRQHandler(void) { data_ready = true; }

int main(void) {
    while (!data_ready) { }   /* without volatile this could become an infinite loop */
}

      volatile does not make an operation atomic. counter++ on a volatile variable is still read, modify and write. An interrupt can arrive between those steps. Protect shared data with a critical section or atomic instructions.

      2.2 const

      • const uint8_t table[] = {...}; usually ends up in Flash (.rodata), which saves RAM.
      • A read-only hardware register: volatile const uint32_t *status_reg; The program must not write to it, but its value can still change.

      2.3 static

      Where Effect
      Local variable Keeps its value between calls. Stored in .data/.bss, not on the stack.
      Global variable or function Visible only inside that .c file (internal linkage).

      2.4 Integer promotion

      Before arithmetic, types smaller than int are promoted to int:

      uint8_t a = 200, b = 100;
uint8_t sum = a + b;    /* a + b is computed as int 300, then truncated to 44 */

      Comparisons that mix signed and unsigned values are a common source of bugs. -1 < 0U is false, because -1 is converted to a large unsigned value.

      Advanced 3. Advanced

      3.1 Memory layout

      Section Contents Located in
      .text Code Flash
      .rodata const data, string literals Flash
      .data Initialised globals and statics RAM (initial values copied from Flash at startup)
      .bss Uninitialised or zero-initialised globals and statics RAM (zeroed at startup)
      Stack Local variables, return addresses RAM (grows down on Cortex-M)
      Heap malloc RAM

      The startup code copies .data, zeroes .bss and then calls main(). Read your toolchain's linker script and .map file to see where everything ends up.

      3.2 Avoid dynamic allocation in real-time code

      malloc/free can fragment the heap, and their run time is not easy to bound. Many safety-related coding standards (for example MISRA C) restrict or forbid dynamic allocation after initialisation. Prefer static buffers or fixed-size memory pools.

      3.3 Implementation-defined and undefined behaviour

      Code Status
      Right shift of a negative signed integer Implementation-defined
      Layout and order of bit-fields Implementation-defined. Don't rely on it for register maps.
      Signed integer overflow Undefined
      Shift by ≥ width of the type Undefined

      3.4 Endianness

      In little-endian order the least-significant byte is stored at the lowest address. Most ARM Cortex-M devices are configured little-endian. Network protocols are often big-endian, so convert explicitly with shifts instead of casting pointers:

      uint32_t be32_read(const uint8_t *p) {
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16) |
           ((uint32_t)p[2] << 8)  |  (uint32_t)p[3];
}

      3.5 Function pointers and state machines

      typedef void (*state_fn)(void);
static void idle(void);
static void run(void);
static state_fn state = idle;

void tick(void) { state(); }   /* each state assigns the next state */

      Expert 4. Expert: C for safety-critical software

      For engineers with 3+ years of experience. Here the focus moves from "does it work?" to "can we prove it works, on this compiler, under every input, and show the evidence to an auditor?"

      4.1 Coding standards: MISRA C and CERT C

      Most safety-related projects adopt a language subset. MISRA C is the most common in avionics, automotive and industrial work. SEI CERT C focuses on security. Your project's coding standard (in DO-178C terms, the Software Code Standards, see Module 5) normally names one of them, plus project rules.

      Key MISRA C:2012 concepts (check the edition your project uses: amendments and a consolidated MISRA C:2023 exist):

      Concept What it means in practice
      Rule categories Mandatory (no deviation allowed), Required (deviation needs a formal, documented record), Advisory
      Decidable vs undecidable rules Some rules can be checked fully by a tool, while others need review or deeper analysis
      Essential type model Treats bool, character, signed, unsigned, enum and floating values as separate categories. It flags implicit conversions that plain C allows, for example mixing signed and unsigned, or assigning to a narrower type.
      Deviations A deviation records the rule, the location, the justification and the review or approval. Blanket "turn the rule off" is not a deviation.

      4.2 Integer traps that pass code review

      These look correct and compile without warnings at default settings:

      uint16_t a = 0xFFFFU, b = 1U;
if ((a + b) == 0U) { ... }      /* 32-bit int: a+b is int 65536, so FALSE.
                                   16-bit int: unsigned arithmetic wraps to 0, so TRUE. */

uint8_t x = 0x0FU;
if ((uint8_t)~x == 0xF0U) { ... }  /* correct */
if (~x == 0xF0U)          { ... }  /* FALSE: ~x is computed as int 0xFFFFFFF0 */

int32_t limit_check(int32_t a) {
    if (a + 100 < a) { /* "overflow check" */ }  /* signed overflow is UB: the compiler may delete this branch */
    return a;
}

      Write overflow checks before the operation: if (a > INT32_MAX - 100) { ... }.

      4.3 Strict aliasing, alignment and type punning

      Accessing an object through a pointer to an incompatible type is undefined behaviour (the "effective type" rules). Optimising compilers rely on this:

      float f = 1.0f;
uint32_t bad  = *(uint32_t *)&f;     /* UB: violates strict aliasing */
uint32_t good;  memcpy(&good, &f, sizeof good);   /* well defined; compilers optimise it to a move */

      Casting a uint8_t receive buffer to a struct pointer has three problems at once: aliasing, alignment (unaligned word access can fault on some cores) and padding or endianness. Parse messages field by field with shifts (see Module 3).

      4.4 Concurrency: volatile is not a synchronisation primitive

      volatile stops the compiler from removing or reordering volatile accesses relative to each other. It does not:

      • order ordinary (non-volatile) memory accesses around it,
      • stop the CPU or memory system from reordering accesses (this matters on multicore and on cores with write buffers), or
      • make read-modify-write sequences atomic.

      For data shared between cores or threads, use C11 <stdatomic.h> (atomic_store_explicit(..., memory_order_release) paired with an acquire load), RTOS primitives, or explicit barriers (on Arm, __DMB() from CMSIS), as your platform documentation requires.

      4.5 Bounded resources: stack, time and memory

      Certification-oriented projects must show that resources are bounded:

      • No recursion. Otherwise the maximum stack depth can't be bounded statically.
      • No dynamic allocation after initialisation (or none at all).
      • Worst-case stack usage comes from static call-graph analysis (many toolchains and analysers report it), plus the interrupt nesting depth. Function pointers and other indirect calls break automatic call graphs unless you annotate them.
      • Worst-case execution time (WCET) for time-critical code. See Module 4.

      4.6 Fixed-point arithmetic

      Many processors used in control software lack an FPU, or projects avoid floating point for determinism. In Q15 format a 16-bit signed value represents −1 … +0.99997:

      int16_t q15_mul(int16_t a, int16_t b) {
    int32_t p = ((int32_t)a * b) >> 15;          /* product fits in 32 bits */
    if (p > INT16_MAX) p = INT16_MAX;            /* -1 * -1 = +1 doesn't fit: saturate */
    return (int16_t)p;
}

      Right shift of a negative value is implementation-defined. Document what your compiler does, or use a defined helper. Your requirements should state the range, resolution and rounding of every fixed-point quantity.

      4.7 Macros, sequence points and evaluation order

      #define MAX(a, b) ((a) > (b) ? (a) : (b))
m = MAX(i++, j);     /* i may be incremented twice. Use a static inline function instead. */

i = i++ + 1;         /* undefined behaviour: i modified twice without sequencing */
f(g(), h());         /* order of evaluating g() and h() is unspecified */

      4.8 Static analysis and compiler behaviour

      • Pattern checkers (MISRA checkers, linters) find rule violations quickly but can miss real defects.
      • Sound analysers based on abstract interpretation aim to prove the absence of run-time errors such as overflow, division by zero and out-of-bounds access, at the cost of false alarms that must be justified.
      • Turn on and review compiler warnings at the strictest practical level, and treat new warnings as defects.
      • The compiler is part of the evidence. Optimisation level and compiler options are configuration items. DO-178C Level A also needs extra verification when the compiler generates object code that isn't directly traceable to source code (see Module 5).

      4.9 Defensive programming and certification

      Defensive checks, such as range checks on inputs or default: branches on enums that "can't happen", are good engineering. In DO-178C projects they must be traceable to requirements, for example robustness requirements, and their coverage must be explained. Unreachable defensive code that isn't covered can show up as a coverage gap that needs analysis. Agree the approach in your plans and standards early.

      Key takeaways

      • Use <stdint.h> types and U suffixes for masks.
      • volatile means "always really access this". It does not mean atomic.
      • Know which sections live in Flash and which in RAM.
      • Avoid undefined behaviour and heap use in time-critical code.
