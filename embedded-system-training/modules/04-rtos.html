      Module 4 — RTOS Fundamentals

      ← Module 3 · Course home · Next: DO-178C → · Take the quiz

      Learning goals

      • Explain tasks, task states and pre-emptive priority scheduling.
      • Choose between a queue, a semaphore and a mutex.
      • Recognise and prevent priority inversion, deadlock and stack overflow.
      • Expert: run response-time analysis, choose resource protocols, and apply ARINC 653 partitioning and multicore guidance.

      The examples use FreeRTOS API names. Other RTOSes (Zephyr, ThreadX, RTX, embOS…) have the same concepts with different names. Check your RTOS documentation for exact signatures, because APIs change between versions.

      Beginner 1. Beginner

      1.1 Why an RTOS?

      A "super-loop" (while(1) { a(); b(); c(); }) is fine for simple systems. As timing requirements grow, an RTOS lets you split the work into tasks with priorities, so urgent work is not held up by slow work.

      Real-time means predictable, not fast:

      • Hard real-time: missing a deadline is a system failure (airbag, motor control).
      • Soft real-time: an occasional miss lowers quality (audio glitch, UI lag).

      1.2 Tasks and states

      Each task has its own stack and a priority. In FreeRTOS a task is in one of these states:

      State Meaning
      Running Currently executing on the CPU
      Ready Able to run, waiting for the CPU
      Blocked Waiting for time or an event (delay, queue, semaphore)
      Suspended Removed from scheduling until explicitly resumed 
      void led_task(void *arg) {
    for (;;) {
        toggle_led();
        vTaskDelay(pdMS_TO_TICKS(500));   /* blocks; other tasks run */
    }
}

xTaskCreate(led_task, "LED", 128, NULL, 1, NULL);
vTaskStartScheduler();

      1.3 The tick

      A periodic timer interrupt (the tick, e.g. configTICK_RATE_HZ = 1000 → 1 ms) drives time-outs and delays. When no task is ready, the idle task runs.

      Intermediate 2. Intermediate

      2.1 Pre-emptive priority scheduling

      The scheduler always runs the highest-priority Ready task. If a higher-priority task becomes ready (for example an ISR gives it a semaphore), it pre-empts the running task immediately. Tasks of equal priority can share the CPU by time slicing.

      During a context switch the RTOS saves the CPU registers of the old task on its stack and restores those of the new task.

      2.2 Inter-task communication

      Object Use it for Notes
      Queue Passing data between tasks, or from an ISR to a task FreeRTOS copies the data into the queue
      Binary semaphore Signalling an event ("data is ready") Often given from an ISR, taken by a task
      Counting semaphore Counting events or a pool of N resources
      Mutex Mutual exclusion around a shared resource Has an owner. FreeRTOS mutexes use priority inheritance.
      Event group Waiting on combinations of flags

      2.3 Calling RTOS functions from ISRs

      In an ISR use only the interrupt-safe variants, e.g. xQueueSendFromISR(), xSemaphoreGiveFromISR(). Request a context switch at the end of the ISR if a higher-priority task was woken (portYIELD_FROM_ISR()). Never call blocking functions from an ISR.

      2.4 Periodic tasks

      vTaskDelay(n) delays relative to now, so the period drifts by however long the work took. For a fixed period use vTaskDelayUntil() (newer FreeRTOS versions also provide xTaskDelayUntil()), which wakes at absolute multiples of the period.

      Advanced 3. Advanced

      3.1 Priority inversion

      A high-priority task waits for a mutex held by a low-priority task, while a medium-priority task pre-empts the low one. The high task is now effectively blocked by the medium task.

      Fix: priority inheritance. The mutex holder temporarily gets the priority of the highest task waiting on it. A widely cited real case is the 1997 Mars Pathfinder lander, which suffered repeated resets until priority inheritance was enabled on a mutex.

      3.2 Deadlock

      Task A holds lock 1 and waits for lock 2, while task B holds lock 2 and waits for lock 1. Prevention:

      • Always take locks in the same global order.
      • Hold locks for as short a time as possible. Don't block while holding one.
      • Use time-outs on take calls and handle failure.

      3.3 Stack sizing

      Each task has its own stack. Overflow corrupts other memory silently.

      • Enable configCHECK_FOR_STACK_OVERFLOW and implement the hook during development.
      • Measure the remaining stack with uxTaskGetStackHighWaterMark() and keep a margin.
      • Large local arrays and deep call chains or printf use a lot of stack.

      3.4 Reentrancy and shared code

      A function is reentrant if it can be safely interrupted and called again before the first call finishes. That means it uses no unprotected static or global state. strtok() is a classic non-reentrant function.

      3.5 Schedulability: rate-monotonic scheduling

      With fixed priorities and periodic independent tasks, giving shorter-period tasks higher priority (rate-monotonic) is optimal among fixed-priority schemes. A sufficient (not necessary) test is:

      U = Σ (Cᵢ / Tᵢ) ≤ n(2^(1/n) − 1)      → about 0.693 for large n

      where Cᵢ is the worst-case execution time and Tᵢ is the period.

      Expert 4. Expert: real-time analysis, partitioning and certified RTOS use

      For engineers with 3+ years of experience: proving deadlines are met, keeping applications of different criticality apart, and what changes when an RTOS is part of DO-178C evidence.

      4.1 Response-time analysis (fixed-priority, pre-emptive)

      The utilisation test in section 3.5 is only sufficient. Response-time analysis gives the exact worst-case response time Rᵢ of task i (independent periodic tasks, deadline ≤ period):

      Rᵢ = Cᵢ + Bᵢ + Σ_{j ∈ hp(i)} ⌈ Rᵢ / Tⱼ ⌉ · Cⱼ

      hp(i) is the set of higher-priority tasks and Bᵢ the worst-case blocking from lower-priority tasks (shared resources). Iterate from Rᵢ = Cᵢ + Bᵢ until the value stops changing. The task is schedulable if Rᵢ ≤ Dᵢ.

      Worked example (B = 0): τ1 C=1 T=4, τ2 C=2 T=6, τ3 C=3 T=12 (priorities in that order). For τ3: R = 3+1+2 = 6 → 3 + ⌈6/4⌉·1 + ⌈6/6⌉·2 = 7 → 3 + 2 + 4 = 9 → 3 + 3 + 4 = 10 → 3 + 3 + 4 = 10. R₃ = 10 ≤ 12, so τ3 meets its deadline.

      The analysis is only as good as the C values. WCET must be justified (see below), and the ISR load and RTOS overheads (tick, context switch) must be included.

      4.2 WCET in practice

      • Measurement alone is not proof. Tests may never drive the worst path or the worst cache state. Use stress scenarios, coverage of the timing-relevant paths and a documented safety margin, or static WCET analysis where a tool supports your processor.
      • Design for analysability: bounded loops with a known maximum iteration count, no recursion, no unbounded waits, and limited use of caches in critical paths.

      4.3 Resource access protocols

      Protocol Behaviour Notes
      Priority inheritance The mutex holder inherits the priority of the highest waiter Bounds inversion, but chained blocking is possible, and it does not prevent deadlock
      Priority ceiling (original and immediate ceiling) The holder runs at the resource's ceiling priority (the highest priority of any task that uses it) On a single core it prevents deadlock and limits blocking to at most one critical section. OSEK/AUTOSAR OS use the immediate-ceiling form.

      In FreeRTOS, a binary semaphore used as a lock has no priority inheritance. Use a mutex.

      4.4 Interrupts and the kernel (FreeRTOS on Cortex-M)

      ISRs that call ...FromISR() APIs must run at a priority logically at or below configMAX_SYSCALL_INTERRUPT_PRIORITY, which on Cortex-M means numerically equal or higher. Higher-urgency interrupts may pre-empt the kernel's critical sections, so they must not call the API at all. Getting this wrong corrupts kernel data structures intermittently. Enable configASSERT() during development, because the port can check this. Exact macro names vary between ports and versions, so check your port's documentation.

      4.5 Deterministic memory

      Allocate statically: xTaskCreateStatic(), xQueueCreateStatic() and so on, with configSUPPORT_DYNAMIC_ALLOCATION set to 0 so that heap use fails at build time instead of in flight.

      4.6 Cyclic executive vs pre-emptive RTOS

      Cyclic executive (time-triggered) Pre-emptive priority RTOS
      Determinism Fixed schedule table, easy to analyse and test Depends on analysis (RTA)
      Change impact Fragile: long tasks must be split by hand to fit minor frames Flexible
      Shared data Often no locking needed, because nothing pre-empts Needs mutexes or ceilings
      Typical use Many high-criticality control loops Mixed workloads

      4.7 Partitioning: ARINC 653 (IMA)

      Integrated Modular Avionics (IMA) runs applications of different software levels on one processor. ARINC 653 defines the partitioning model and the APEX API:

      • Time partitioning: a fixed major frame is divided into partition windows. A partition that overruns can't take time from the others.
      • Space partitioning: each partition has its own memory, enforced by the MMU or MPU.
      • Health monitor: detects errors at process, partition and module level and applies the configured response (restart a process, restart a partition, shut down, log).
      • Communication between partitions goes through ports (sampling and queuing).

      Robust partitioning is what allows, for example, a Level C application to share a processor with a Level A application without the Level C software being developed to Level A. The partitioning itself must be shown to be robust (see Module 5).

      4.8 Multicore

      Cores interfere through shared caches, interconnects and memory controllers, so one core's WCET depends on what the others do. Certification guidance for multicore processors in airborne systems started as the position paper CAST-32A and has since been followed by EASA AMC 20-193 and FAA AC 20-193. Check the current status with your certification authority. Expect to identify interference channels, mitigate them (for example by cache or bandwidth partitioning) and verify timing under worst-case interference.

      4.9 Using an RTOS in a certified system

      • An RTOS used in airborne software is part of that software. It needs DO-178C life-cycle data at the applicable software level, either from the vendor (a "certification package") or produced by the project.
      • Use only the subset of RTOS features covered by that data, and document configuration settings as configuration items.
      • Supervise task health: a supervisor task collects check-ins from every critical task and kicks the watchdog only when all have reported within their deadlines.

      Key takeaways

      • The highest-priority Ready task runs. Blocked tasks consume no CPU.
      • Use a queue for data, a semaphore for signals and a mutex for shared resources.
      • Use only ...FromISR APIs inside interrupts.
      • Watch for priority inversion, deadlock and stack overflow.
