        Module 5 — DO-178C: Airborne Software Certification

        ← Module 4 · Course home · Take the quiz

        Learning goals

        • Explain where DO-178C sits in aircraft certification, and how software levels are assigned.
        • Name the planning documents, standards and life-cycle data a project produces.
        • Apply requirements-based testing, structural coverage (including MC/DC) and traceability correctly.
        • Handle the expert topics that cause most audit findings: derived requirements, dead and deactivated code, coverage gaps, tool qualification, previously developed software and multicore.

        About this module. DO-178C is a copyrighted RTCA document (published in Europe by EUROCAE as ED-12C). This module is a summary for training. It is not a substitute for the document itself, for its Annex A objective tables, or for the guidance of your certification authority (FAA, EASA or others). Where a number or document revision is quoted, check it against the primary source before relying on it in a project.

        Beginner 1. Beginner — what DO-178C is

        1.1 Purpose

        DO-178C, Software Considerations in Airborne Systems and Equipment Certification (RTCA, 2011), gives objectives for the software life cycle, the activities that satisfy them, and the evidence (life-cycle data) that shows they were satisfied. Certification authorities recognise it as an acceptable means of compliance for airborne software. In the US this is through an FAA Advisory Circular (AC 20-115, currently revision D; verify the current revision).

        DO-178C doesn't prescribe a language, a tool or a development model. It requires that you plan how you'll meet the objectives, do what you planned, and prove it.

        1.2 Where it fits

        Aircraft / system level        ARP4754A (now ARP4754B) system development,  ARP4761 safety assessment
        │  system requirements allocated to software + software level
        ▼
Software                       DO-178C  (+ supplements DO-330 tools, DO-331 models,
                                         DO-332 object-oriented, DO-333 formal methods)
Hardware (complex electronics) DO-254

        1.3 Software levels

        The system safety assessment, not the software team, assigns the software level from the most severe failure condition the software can cause or contribute to:

        Level Failure condition category Structural coverage required
        A Catastrophic MC/DC + decision + statement
        B Hazardous / Severe-Major Decision + statement
        C Major Statement
        D Minor None
        E No safety effect DO-178C objectives don't apply

        Higher levels have more objectives, and more of them must be satisfied with independence (verified by someone other than the author). Commonly cited objective counts for DO-178C are 71 (A), 69 (B), 62 (C) and 26 (D). Confirm them against the Annex A tables.

        Intermediate 2. Intermediate — processes, plans and data

        2.1 Life-cycle processes

        Process Main content
        Planning Defines how every objective will be met: life cycle, standards, tools, environment, transition criteria
        Development Requirements → design → coding → integration
        Verification Reviews, analyses and tests of every development output
        Configuration management (SCM) Identification, baselines, change control, problem reporting, archiving
        Quality assurance (SQA) Independent assurance that plans and standards were followed; conformity review
        Certification liaison Communication and agreement with the certification authority

        2.2 The five plans and three standards

        Document Purpose
        PSAC, Plan for Software Aspects of Certification The primary agreement with the authority: system overview, software level, life cycle, means of compliance, tools, additional considerations
        SDP, Software Development Plan Development life cycle, standards and environment
        SVP, Software Verification Plan Verification methods, independence, environment, coverage approach
        SCMP, Software Configuration Management Plan Baselines, change control, problem reports, archiving
        SQAP, Software Quality Assurance Plan SQA activities, audits, conformity review
        Software Requirements, Design and Code Standards Rules that the outputs must follow, and that reviews check

        2.3 Development outputs

        System requirements allocated to software
   └─► High-level requirements (HLR)          what the software must do
         └─► Software architecture + low-level requirements (LLR)   how, detailed enough to code from
               └─► Source code
                     └─► Executable object code (+ parameter data items)
        • Derived requirements are requirements that don't trace directly to a higher-level requirement, for example a design decision such as "the filter runs at 100 Hz". They must be identified and provided to the system safety assessment process so their safety impact is evaluated.
        • Parameter data items (new in DO-178C), such as configuration tables, are data that change behaviour without changing executable code. They have their own verification objectives.

        2.4 Other key life-cycle data

        Software Verification Cases and Procedures (SVCP), Software Verification Results (SVR), Software Configuration Index (SCI), Software Life Cycle Environment Configuration Index (SECI), Problem Reports, SCM and SQA Records, and finally the Software Accomplishment Summary (SAS), which states how compliance with the PSAC was achieved.

        2.5 Working with the authority

        Authorities review progress at defined points. FAA practice calls these Stages of Involvement (SOI 1 planning, SOI 2 development, SOI 3 verification, SOI 4 final). The details come from authority guidance and orders, not from DO-178C itself, so check your authority's current procedures.

        Advanced 3. Advanced — verification

        3.1 Reviews and analyses

        Each development output is reviewed or analysed for compliance with its parent, accuracy and consistency, compatibility with the target, verifiability, conformance to standards, traceability, and (for code and integration) algorithm correctness. Checklists in the plans make these reviews repeatable.

        3.2 Requirements-based testing

        • Tests are derived from requirements, never from the code.
        • Test both normal range (equivalence classes, boundary values, time-related functions, state transitions) and robustness (invalid inputs, out-of-range values, failure modes, abnormal timing).
        • Test levels: hardware/software integration testing on the target, software integration testing, and low-level testing against LLRs.
        • Run tests on the target hardware, or in an environment whose equivalence is justified.

        3.3 Structural coverage analysis

        Coverage measures how thoroughly the requirements-based tests exercised the code. It is an analysis of completeness, not a way of creating tests.

        Criterion Meaning
        Statement Every statement executed at least once
        Decision Every decision took both outcomes, and every entry and exit point was invoked
        MC/DC Decision coverage, plus every condition took all outcomes and was shown to independently affect the decision's outcome

        The next section explains MC/DC in depth, including how many tests each kind of decision needs.

        Also required at Levels A–C: analysis that the tests exercised the data coupling and control coupling between components, that is, the interfaces actually used in the integrated software.

        3.4 MC/DC in depth

        Vocabulary

        Term Meaning (DO-178C sense, paraphrased)
        Condition A Boolean expression with no Boolean operators except NOT, for example speed > V_MAX, valid, !door_open
        Decision A Boolean expression made of conditions and zero or more Boolean operators, for example valid && (speed > V_MAX). If a condition appears more than once, each occurrence counts as a separate condition.
        Independence pair Two tests that show one condition, on its own, changes the decision's outcome

        Note: a decision isn't only the expression in an if. An assignment such as alarm = valid && over_limit; is also a Boolean expression with operators, and is normally treated as a decision for MC/DC. FAA position paper CAST-10 discusses this. Agree the interpretation, and how your coverage tool handles it, in your plans.

        The rule in one picture

        To show that condition X independently affects the outcome, find two tests in which only X changes and the outcome changes. The other conditions must be set so they don't "block" X:

        How many tests? Minimum unique-cause MC/DC sets

        Decision Others held at… A minimal test set (outcome) Tests
        A n/a T (T), F (F) 2
        A && B TRUE TT (T), FT (F), TF (F) 3
        A && B && C TRUE TTT (T), FTT (F), TFT (F), TTF (F) 4
        A || B FALSE FF (F), TF (T), FT (T) 3
        A || B || C FALSE FFF (F), TFF (T), FTF (T), FFT (T) 4
        !(A && B) NOT adds no condition TT (F), FT (T), TF (T) 3
        A != B (XOR of two Booleans) Any change flips the outcome FF (F), TF (T), FT (T) 3
        (A && B) || C See worked example 2 TTF (T), FTF (F), TFF (F), TFT (T) 4
        A || (B && C) A needs B && C = F; B and C need A = F FTT (T), FFT (F), FTF (F), TTF (T) 4

        For N independent conditions, unique-cause MC/DC needs at least N+1 tests (the upper bound is commonly quoted as 2N). Compare that with multiple condition coverage, which tests every combination (2ᴺ). DO-178C doesn't require multiple condition coverage:

        Conditions N MC/DC minimum (N+1) All combinations (2ᴺ)
        2 3 4
        3 4 8
        4 5 16
        5 6 32
        10 11 1 024

        Tip: every truth table and test count in this section was checked with the repository's helper, node tools/mcdc.js "(A&&B)||C" TTF FTF TFF TFT, which prints the independence pairs and whether a test set achieves unique-cause MC/DC.

        Worked example 1: if (A && B && C)

        The decision is TRUE only for TTT. Each FALSE row that differs from TTT in exactly one condition forms that condition's independence pair with TTT. The selected rows are highlighted:

        #ABCOutcomeUse
        1TTTTbaseline for all three pairs
        2FTTFpair (1, 2) shows A
        3TFTFpair (1, 3) shows B
        4TTFFpair (1, 4) shows C
        5FFTFnot needed
        6FTFFnot needed
        7TFFFnot needed
        8FFFFnot needed

        Result: 4 tests (rows 1–4), which is N+1.

        Worked example 2: if ((A && B) || C)

        ABCA && BOutcomeIndependence pairs this row belongs to
        FFFFFC (with FFT)
        FFTFTC (with FFF)
        FTFFFA (with TTF); C (with FTT)
        FTTFTC (with FTF)
        TFFFFB (with TTF); C (with TFT)
        TFTFTC (with TFF)
        TTFTTA (with FTF); B (with TFF)
        TTTTTnone: C is masked because A && B is already TRUE
        • A has exactly one pair, FTF/TTF: B must be TRUE and C FALSE.
        • B has exactly one pair, TFF/TTF: A must be TRUE and C FALSE.
        • C has three possible pairs. Choose one that reuses tests you already have: TFF/TFT.
        • Minimal set: TTF, FTF, TFF, TFT, which is 4 tests (N+1). TTF, FTF, TFF, FTT works too.

        Decision coverage is not MC/DC

        For A && B, the two tests TT (T) and FF (F) give 100 % decision coverage, but no independence pair: both conditions change together, so the tests can't show which one caused the outcome. A defect such as A || B written instead of A && B would also pass both tests (TT gives T, FF gives F). MC/DC (TT, FT, TF) catches it, because FT and TF would return T instead of F.

        Short-circuit evaluation in C

        && and || evaluate left to right and stop as soon as the result is known. In if (A && B) with A = FALSE, B is never evaluated. Coverage tools and analyses commonly treat it as "don't care" (x), so A's independence pair is TT (T) vs Fx (F).

        TestABOutcomeShows
        1TTTbaseline
        2Fx (not evaluated)FA (vs 1)
        3TFFB (vs 1)

        Warning: because the right operand may not run, MISRA C:2012 (Rule 13.5) forbids persistent side effects in the right-hand operand of && and ||, for example if (ok && read_sensor(&v)). Check the rule against the edition your project uses.

        Unique-cause vs masking MC/DC

        Variant What may change between the two tests of a pair
        Unique-cause Only the condition being shown
        Masking Other conditions may change too, if their effect on the outcome is masked, for example by an AND input that is FALSE

        Masking is needed when conditions are coupled. In (A && B) || (A && C), A appears twice, so the two occurrences always change together, and unique-cause pairs are impossible for each occurrence. To show the first A, mask the second term by setting C = FALSE:

        • (A=T, B=T, C=F) → TRUE, and (A=F, B=T, C=F) → FALSE.
        • The second A also changed, but A && C is FALSE in both tests because C = FALSE, so its change is masked.

        FAA position paper CAST-6 discusses the rationale for accepting masking MC/DC. State the variant you use in your PSAC/SVP, and make sure your coverage tool measures the same variant.

        Practical rules

        1. Design tests from requirements first, run them, then measure MC/DC. Missing pairs point to missing requirements, inadequate tests, or redundant conditions in the code (see 3.5).
        2. A condition that can never get an independence pair, for example if (x > 10 && x > 5) where the second condition is redundant, usually means a design or code defect, not a testing problem.
        3. Bitwise operators on Boolean values (&, |) can hide decisions from some tools. Follow your coding standard, which usually requires &&/|| for Boolean logic.
        4. Splitting a complex decision into nested ifs can improve readability, but do it for the design, not to make coverage look easier. Reviewers check that the requirements are still fully tested.

        Tip: practise with the dedicated Coverage & MC/DC quiz: 16 worked questions on test sets, short-circuit evaluation, masking and coverage gaps.

        3.5 Resolving coverage gaps

        When code isn't covered, find out why:

        Cause Resolution
        Missing or incomplete requirement Fix the requirements, then add requirements-based tests
        Inadequate test Add or improve requirements-based tests
        Dead code: exists by mistake and doesn't trace to requirements Remove it, and assess whether re-verification is needed
        Deactivated code: intentional, but unused in this configuration Show by design and verification that it can't be activated by accident, and verify it for the configurations where it is used
        Defensive code that can't be reached Justify, with traceability to the requirement or standard that calls for it, as agreed in your plans

        Don't write a "test" whose only purpose is to execute uncovered code with no requirement behind it. That hides the real problem: either a missing requirement or unwanted code.

        3.6 Traceability

        Bidirectional traceability is required: system requirements ↔ HLR ↔ LLR ↔ source code, and requirements ↔ test cases ↔ procedures ↔ results. Traceability shows that every requirement is implemented and verified, and that there is no unintended functionality.

        Expert 4. Expert — topics that decide audits

        4.1 Level A: source-to-object code

        At Level A, if the compiler or linker generates object code that isn't directly traceable to source code (for example inserted range checks, library calls or complex optimisations), additional verification is needed to establish the correctness of that generated code. Projects typically restrict compiler options and constructs, and analyse the object code for the remaining cases.

        4.2 Tool qualification (DO-330)

        A tool needs qualification when it eliminates, reduces or automates a DO-178C process and its output is not verified. The Tool Qualification Level (TQL) depends on the tool's impact and the software level:

        Criterion Meaning Level A B C D
        1 Its output is part of the airborne software, so it could insert an error (for example a code generator) TQL-1 TQL-2 TQL-3 TQL-4
        2 Automates verification, and its output is used to justify eliminating or reducing other verification or development processes TQL-4 TQL-4 TQL-5 TQL-5
        3 Automates verification, so it could only fail to detect an error TQL-5 TQL-5 TQL-5 TQL-5

        TQL-1 is the most rigorous. Compilers are normally not qualified: their output is verified instead, through testing of the executable object code (plus the Level A analysis above). Confirm the table against DO-178C section 12.2 and DO-330.

        4.3 Supplements

        Supplement Use when
        DO-330 Qualifying software tools (also usable outside airborne software)
        DO-331 Model-based development and verification, for example design models from which code is generated
        DO-332 Object-oriented technology: inheritance, dynamic dispatch, dynamic memory, exceptions
        DO-333 Formal methods used to replace or complement reviews, analyses or tests

        DO-248C contains supporting information (FAQs and discussion papers). It explains DO-178C but adds no new objectives.

        4.4 Previously developed software, COTS and RTOS

        Reusing software (an RTOS, a library, a previous program's code) requires assessing the available life-cycle data against the objectives for the new software level and environment. Typical issues are missing low-level requirements, missing structural coverage, a changed compiler or target, and changed use. Gaps are filled by additional activities, or occasionally by alternative methods agreed in the PSAC. Changes to the software, its use or its environment need a change impact analysis.

        4.5 Partitioning and multicore

        • Partitioning (for example ARINC 653) can contain the effects of a lower-level application, but the partitioning mechanism itself must be developed and verified at the level of the most critical software it protects, and shown to be robust against faults in the partitions (see Module 4).
        • Multicore processors need additional analysis of interference between cores. See CAST-32A and its successors, EASA AMC 20-193 and FAA AC 20-193, and agree the approach in the PSAC.

        4.6 Configuration management in practice

        • Two control categories, CC1 (full SCM: baselines, change control, problem reporting, release, archiving) and CC2 (a reduced set). Annex A says which category applies to each data item at each level.
        • Every item that affects the delivered software is under configuration control: source, build scripts, compiler version and options, linker files, test procedures, tool versions and parameter data.
        • The build must be reproducible from the archived configuration.

        4.7 Common findings and how to avoid them

        Finding Prevention
        Requirements that restate the code ("set flag X to 1") HLR describe behaviour at the system interface. LLR are detailed design, but still verifiable without reading the code.
        Derived requirements not sent to safety Mark them in the requirements tool and track them in a regular safety-review loop
        Tests that check code structure instead of requirements Peer-review test cases against requirements and standards
        Coverage achieved, robustness missing Robustness tests are explicit in the SVP and checklists
        Plans not followed (or followed but not updated) Treat plans as living documents and update them through the CM process. SQA audits compare plans with practice.
        Tools used without qualification decision Keep a tool list with the qualification rationale for each tool in the PSAC/SECI
        Independence not demonstrated Record who authored and who verified each item

        Key takeaways

        • The safety assessment sets the software level, and the level sets the objectives, independence and coverage.
        • Plan, follow the plans, and keep the evidence: plans, standards, traceability, reviews, tests, coverage, CM and SQA records.
        • Coverage analysis checks the completeness of requirements-based tests. It doesn't create tests.
        • Dead code is removed. Deactivated code is shown to be safely deactivated. Derived requirements go to safety.
        • Tools that can insert errors, or that replace verification, may need qualification under DO-330.

        Self-check

        1. A Level B component reaches 100 % statement and decision coverage. Is MC/DC required?
        2. Coverage analysis finds an uncovered else branch that no requirement asks for. What are the possible resolutions?
        3. Which tool qualification criterion applies to a tool that generates C code from a model, for Level A software?
