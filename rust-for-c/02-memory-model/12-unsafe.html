Rust for C Programmers

Raw pointers and unsafe

In C

Every pointer is raw. You may add, subtract, cast, compare, and dereference any pointer anywhere, and the compiler trusts you completely.

int a[3] = {1, 2, 3};
int *p = a;
int x = *(p + 2);          /* pointer arithmetic */
*(char *)p = 0;            /* reinterpret memory */

In Rust

Rust has the same raw pointers, *const T and *mut T, but they live behind a marker. Code that can break memory safety must be in an unsafe block or unsafe fn. The vast majority of Rust code never needs it.

fn main() {
    let mut x = 10;
    let p = &mut x as *mut i32;   // creating a raw pointer is safe
    unsafe {
        *p += 5;                  // dereferencing is the unsafe part
    }
    println!("{x}");              // 15
}

What unsafe allows (and only this)

Inside an unsafe block you gain five extra abilities:

  1. dereference a raw pointer,
  2. call an unsafe function (including C functions through FFI),
  3. access or modify a static mut,
  4. implement an unsafe trait (such as Send),
  5. read a field of a union.

What unsafe does not do

It does not turn off the type checker or the borrow checker. Ordinary references inside an unsafe block are still checked. It only means: “for these operations, the compiler cannot verify safety, so I take responsibility.”

You are still bound by the rules; breaking them is undefined behavior, as in C: no dangling or null dereference, no data races, no aliasing a &mut, no invalid values (a bool that is not 0 or 1), and so on.

Pointer arithmetic

fn main() {
    let a = [1, 2, 3];
    let p = a.as_ptr();                    // *const i32 to the first element
    unsafe {
        for i in 0..a.len() {
            print!("{} ", *p.add(i));      // like *(p + i); counts in elements
        }
    }
    println!();

    let null: *const i32 = std::ptr::null();
    println!("{}", null.is_null());        // true; *null would be UB
}

Building a safe API on unsafe

The idiom is to keep unsafe small, check its preconditions, and expose a safe function. The standard library does this everywhere. Here is split_at_mut: two non-overlapping &mut slices of one array, which the borrow checker cannot verify by itself.

use std::slice;

fn split_at_mut(xs: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = xs.len();
    let p = xs.as_mut_ptr();
    assert!(mid <= len);                        // the safety condition, checked
    unsafe {
        (
            slice::from_raw_parts_mut(p, mid),
            slice::from_raw_parts_mut(p.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut a = [1, 2, 3, 4, 5];
    let (left, right) = split_at_mut(&mut a, 2);
    left[0] = 10;
    right[0] = 30;
    println!("{a:?}");                          // [10, 2, 30, 4, 5]
}

Callers of split_at_mut need no unsafe and cannot misuse it.

unsafe fn and documenting the contract

/// # Safety
/// `p` must be non-null, aligned, and point to a valid, initialized `i32`.
unsafe fn read(p: *const i32) -> i32 {
    unsafe { *p }
}

fn main() {
    let x = 7;
    let v = unsafe { read(&x) };               // caller promises the contract
    println!("{v}");
}

Boxes to raw pointers and back

This is the Rust analogue of handing ownership across an API boundary:

fn main() {
    let p: *mut i32 = Box::into_raw(Box::new(42));   // ownership leaves Rust's hands
    unsafe {
        *p += 1;
        let b = Box::from_raw(p);                    // take it back: freed on drop
        println!("{}", *b);                          // 43
    }
}

Forgetting from_raw leaks; calling it twice is a double free.

Uninitialized memory: MaybeUninit

Safe Rust never lets you read an uninitialized variable. When you really need a buffer that is filled piece by piece, such as an array built in a loop or memory handed to a C function, MaybeUninit<T> is the type that may hold garbage. You write each element first, and only then claim it is initialized:

use std::mem::MaybeUninit;

fn main() {
    let mut arr: [MaybeUninit<u32>; 4] = [const { MaybeUninit::uninit() }; 4];
    for (i, slot) in arr.iter_mut().enumerate() {
        slot.write(i as u32 * 10);
    }
    // SAFETY: every element was written in the loop above.
    let arr: [u32; 4] = unsafe { std::mem::transmute(arr) };
    println!("{arr:?}");   // [0, 10, 20, 30]
}

Calling assume_init (or the transmute above) on memory that is not fully written is undefined behavior, exactly like reading an uninitialized int in C. The safe alternatives ([0; 4], Vec::with_capacity plus push) are almost always enough; reach for MaybeUninit when you have measured a need.

Raw pointers without references: &raw

Creating a reference &x promises that it is valid and aligned. Sometimes you must not make that promise, for example for a field of a #[repr(packed)] struct, which may sit at an odd address. &raw const and &raw mut produce a raw pointer directly, with no reference in between:

#[repr(C, packed)]
struct Header {
    tag: u8,
    len: u32,       // unaligned: bytes 1..5
}

fn main() {
    let h = Header { tag: 1, len: 7 };
    let p = &raw const h.len;
    // SAFETY: `p` points into `h`, which is alive; the read does not assume alignment.
    println!("{}", unsafe { p.read_unaligned() });   // 7
}

The same syntax is how you touch a static mut without creating a reference to it, which edition 2024 rejects by default.

Under the hood

  • A raw pointer has the same representation as a C pointer: one machine word (two for a pointer to a slice or trait object). A dereference compiles to a plain load or store.
  • unsafe has no runtime cost and no effect on code generation. It is a compile-time marker for humans and tools.
  • Undefined behavior in unsafe can break the guarantees of the safe code around it. That is why unsafe blocks should be tiny and wrapped in safe APIs.
  • To catch UB in tests, run cargo +nightly miri test. It interprets your code and detects invalid reads, dangling pointers and aliasing violations.

C habits to unlearn

  • Do not use raw pointers for ordinary work. Use references, slices, Vec and Box, which are checked.
  • Do not write unsafe to “make the borrow checker quiet”. Restructure the data first.
  • Do not leave unsafe code undocumented. State the contract (# Safety) and check it in the safe wrapper.
  • Do not assume anything works “because it does in C”: Rust’s aliasing rules for &/&mut are stricter, even inside unsafe.

Exercises

  1. Write fn swap_raw(a: *mut i32, b: *mut i32) using unsafe, then a safe wrapper fn swap(a: &mut i32, b: &mut i32) that calls it.

  2. Use Box::into_raw and drop the box with Box::from_raw. Then comment out from_raw and think about what leaked.

  3. Search the Rust source for unsafe in Vec::push‘s implementation (via the docs’ [src] link) and read the safety comments.

  4. Complete the code. Write a safe read_at that checks the index, then reads through a raw pointer inside a small unsafe block.

  5. Write and test. Build an array of the first four squares with MaybeUninit: write each element, then convert. Assert the result is [0, 1, 4, 9].

Solutions

1.

/// # Safety
/// `a` and `b` must be valid, aligned and writable.
unsafe fn swap_raw(a: *mut i32, b: *mut i32) {
    unsafe {
        let t = *a;
        *a = *b;
        *b = t;
    }
}

fn swap(a: &mut i32, b: &mut i32) {
    // SAFETY: references are non-null, aligned and valid for writes.
    unsafe { swap_raw(a, b) }
}

fn main() {
    let (mut x, mut y) = (1, 2);
    swap(&mut x, &mut y);
    println!("{x} {y}");   // 2 1
}

The safe wrapper is the point: the unsafe block is one line, and its safety argument follows from the types of the parameters.

2.

fn main() {
    let p: *mut i32 = Box::into_raw(Box::new(42));
    unsafe {
        println!("{}", *p);
        drop(Box::from_raw(p));   // gives ownership back, then frees it
    }
}

If you comment out the from_raw line, the heap allocation is never freed: it leaks, like a malloc without free. This is safe Rust (leaking is not undefined behavior), and a leak checker such as Valgrind or Miri reports it.

3. Things to look for in the source of Vec::push: an unsafe block that writes the new element into spare capacity, after code that guarantees the capacity is large enough, and a comment that states that precondition. This is the pattern from this chapter: a small unsafe core with a stated contract, wrapped in a safe API.

4.

fn read_at(v: &[i32], i: usize) -> Option<i32> {
    if i < v.len() {
        // SAFETY: `i` is in bounds, so the pointer is valid and aligned.
        Some(unsafe { *v.as_ptr().add(i) })
    } else {
        None
    }
}

fn main() {
    assert_eq!(read_at(&[1, 2, 3], 1), Some(2));
    assert_eq!(read_at(&[1, 2, 3], 3), None);
    println!("ok");
}

(v.get(i).copied() does all of this safely; the exercise shows the shape of a safe wrapper around an unsafe core.)

5.

use std::mem::MaybeUninit;

fn squares() -> [u32; 4] {
    let mut arr: [MaybeUninit<u32>; 4] = [const { MaybeUninit::uninit() }; 4];
    for (i, slot) in arr.iter_mut().enumerate() {
        slot.write((i * i) as u32);
    }
    // SAFETY: every element was written in the loop.
    unsafe { std::mem::transmute(arr) }
}

fn main() {
    assert_eq!(squares(), [0, 1, 4, 9]);
    println!("ok");
}

If the loop wrote only three elements, the transmute would still compile, and the program would have undefined behavior: that is what unsafe means.
