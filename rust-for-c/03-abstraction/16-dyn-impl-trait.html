Rust for C Programmers

dyn Trait and impl Trait

In C

When the concrete type is only known at run time, C uses a vtable: a struct of function pointers, plus a void * to the object.

struct shape_vtable {
    double (*area)(const void *self);
};

struct shape {
    const struct shape_vtable *vt;
    const void *self;
};

struct circle { double r; };

static double circle_area(const void *self) {
    const struct circle *c = self;          /* the cast is on you */
    return 3.14159 * c->r * c->r;
}
static const struct shape_vtable circle_vt = { circle_area };

/* struct shape s = { &circle_vt, &my_circle };  call: s.vt->area(s.self) */

You maintain the table, the casts, and the pairing of table with object by hand.

In Rust

A trait object, written dyn Trait, is exactly that pair, built and checked by the compiler. It is used behind a pointer: &dyn Trait, Box<dyn Trait>.

trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> &str;
}

struct Circle(f64);
struct Rect(f64, f64);

impl Shape for Circle {
    fn area(&self) -> f64 { 3.14159 * self.0 * self.0 }
    fn name(&self) -> &str { "circle" }
}
impl Shape for Rect {
    fn area(&self) -> f64 { self.0 * self.1 }
    fn name(&self) -> &str { "rect" }
}

fn main() {
    // one collection, different concrete types
    let shapes: Vec<Box<dyn Shape>> = vec![Box::new(Circle(1.0)), Box::new(Rect(2.0, 3.0))];
    for s in &shapes {
        println!("{} {}", s.name(), s.area());     // dynamic dispatch
    }
    let total: f64 = shapes.iter().map(|s| s.area()).sum();
    println!("{total}");
}

dyn Shape itself has no known size, so it cannot be a local or a Vec element directly; it must sit behind a pointer:

trait Shape { fn area(&self) -> f64; }
struct Circle(f64);
impl Shape for Circle { fn area(&self) -> f64 { self.0 } }

fn main() {
    let s: dyn Shape = Circle(1.0);   // error[E0277]: the size for values of type `dyn Shape` cannot be known
                                      // (rustc also reports E0308 mismatched types here)
}

Use generics by default; use dyn when you need a heterogeneous collection, a plugin-style boundary, or want to limit code bloat.

impl Trait in arguments and return types

impl Trait is short for “some specific type implementing this trait”. In an argument it is a generic with the name left out:

trait Shape { fn area(&self) -> f64; }
struct Square(f64);
impl Shape for Square { fn area(&self) -> f64 { self.0 * self.0 } }

fn describe(s: &impl Shape) -> String {       // same as fn describe<T: Shape>(s: &T)
    format!("area = {}", s.area())
}

fn main() {
    println!("{}", describe(&Square(3.0)));
}

In a return position it hides a type that you cannot or do not want to name, such as a closure or an iterator chain. It is still one concrete type, resolved at compile time:

fn evens(limit: u32) -> impl Iterator<Item = u32> {
    (0..limit).filter(|x| x % 2 == 0)
}

fn main() {
    let v: Vec<u32> = evens(10).collect();
    println!("{v:?}");                         // [0, 2, 4, 6, 8]
}

To return one of several different types at run time, return Box<dyn Trait>.

Dyn compatibility (object safety)

Only some traits can become dyn; the Reference calls them dyn compatible (older texts say object safe). A method must not be generic and must not return Self by value, because the compiler cannot build a single vtable entry for it. A method can opt out with where Self: Sized, which keeps it callable on concrete types and leaves it out of the vtable. Traits that are not dyn compatible can still be used as generic bounds.

Under the hood

A &dyn Shape is a fat pointer of two words: a pointer to the data and a pointer to a vtable, the same layout as the C pair above.

use std::mem::size_of;

trait Shape { fn area(&self) -> f64; }

fn main() {
    println!("{}", size_of::<&dyn Shape>() == 2 * size_of::<usize>());     // true
    println!("{}", size_of::<Box<dyn Shape>>() == 2 * size_of::<usize>()); // true
}
 &dyn Shape (2 words)         vtable for Circle as Shape
 ┌────────────┐               ┌──────────────────────┐
 │ data ptr   │──▶ Circle     │ drop_in_place        │
 │ vtable ptr │─────────────▶ │ size, align          │
 └────────────┘               │ area()               │
                              └──────────────────────┘
  • Besides method pointers, the vtable holds the size, alignment and a destructor, so a Box<dyn Shape> can be freed correctly.
  • A dyn call is an indirect call; the optimizer usually cannot inline it, which is the same cost as the C vtable.

C habits to unlearn

  • Do not hand-roll vtables and casts. Declare a trait and a dyn.
  • Do not use dyn only to avoid writing generics; you give up inlining.
  • Do not return a closure by function pointer. Use impl Fn or Box<dyn Fn>.

Exercises

  1. Add a third shape and put it in the Vec<Box<dyn Shape>>. Did you change any existing code?

  2. Replace Vec<Box<dyn Shape>> with Vec<&dyn Shape> using references to locals.

  3. Write fn pick(flag: bool) -> Box<dyn Shape> that returns a Circle or a Rect. Why does the same signature with impl Shape fail?

  4. Complete the code. Give Animal a default method speak that returns "<name> says <sound>", then use it through trait objects.

    trait Animal {

Solutions

1.

trait Shape {
    fn area(&self) -> f64;
}

struct Circle(f64);
struct Rect(f64, f64);
struct Square(f64);       // the new shape

impl Shape for Circle { fn area(&self) -> f64 { 3.14159 * self.0 * self.0 } }
impl Shape for Rect { fn area(&self) -> f64 { self.0 * self.1 } }
impl Shape for Square { fn area(&self) -> f64 { self.0 * self.0 } }

fn main() {
    let shapes: Vec<Box<dyn Shape>> = vec![
        Box::new(Circle(1.0)),
        Box::new(Rect(2.0, 3.0)),
        Box::new(Square(2.0)),
    ];
    let total: f64 = shapes.iter().map(|s| s.area()).sum();
    println!("{total}");
}

No existing code changed: only the new type and its impl, and one more element in the vector. Adding a shape to a C tagged union means editing every switch.

2.

trait Shape {
    fn area(&self) -> f64;
}

struct Circle(f64);
struct Rect(f64, f64);

impl Shape for Circle { fn area(&self) -> f64 { 3.14159 * self.0 * self.0 } }
impl Shape for Rect { fn area(&self) -> f64 { self.0 * self.1 } }

fn main() {
    let c = Circle(1.0);
    let r = Rect(2.0, 3.0);
    let shapes: Vec<&dyn Shape> = vec![&c, &r];
    for s in &shapes {
        println!("{}", s.area());
    }
}

No heap allocation is needed. The locals must outlive the vector.

3.

trait Shape { fn area(&self) -> f64; }
struct Circle(f64);
struct Rect(f64, f64);
impl Shape for Circle { fn area(&self) -> f64 { 3.14159 * self.0 * self.0 } }
impl Shape for Rect { fn area(&self) -> f64 { self.0 * self.1 } }

fn pick(flag: bool) -> Box<dyn Shape> {
    if flag { Box::new(Circle(1.0)) } else { Box::new(Rect(2.0, 3.0)) }
}

fn main() {
    println!("{}", pick(true).area());
}

impl Shape in return position means “one concrete type, which I will not name”. The function body must return the same type on every path:

#![allow(unused)]
fn main() {
trait Shape {}
struct Circle;
struct Rect;
impl Shape for Circle {}
impl Shape for Rect {}

fn pick(flag: bool) -> impl Shape {
    if flag { Circle } else { Rect }   // error[E0308]: `if` and `else` have incompatible types
}
}

4. Replace the body of speak with:

trait Animal {
    fn name(&self) -> String;
    fn sound(&self) -> String;
    fn speak(&self) -> String {
        format!("{} says {}", self.name(), self.sound())
    }
}

struct Dog;
impl Animal for Dog {
    fn name(&self) -> String { "Dog".into() }
    fn sound(&self) -> String { "woof".into() }
}

fn main() {
    let zoo: Vec<Box<dyn Animal>> = vec![Box::new(Dog)];
    assert_eq!(zoo[0].speak(), "Dog says woof");
    println!("ok");
}

A default method is written once in the trait and works for every type that implements it, with dynamic dispatch for name and sound.

5.

fn evens() -> impl Iterator<Item = u32> {
    (0..).step_by(2)
}

fn main() {
    let v: Vec<u32> = evens().take(3).collect();
    assert_eq!(v, [0, 2, 4]);
    println!("ok");
}

The concrete iterator type is hidden from the caller but known to the compiler, so the call is inlined and there is no heap allocation.
