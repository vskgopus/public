Rust for C Programmers

Concurrency

In C

Threads share all memory by default. Data races are undefined behavior, and the compiler does not know which variables a mutex protects. The mutex and the data it guards are separate objects, tied together only by discipline.

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
long counter;                       /* nothing says `lock` protects this */

void *worker(void *arg) {
    for (int i = 0; i < 1000; i++) {
        pthread_mutex_lock(&lock);
        counter++;                  /* forget the lock: data race, UB */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

In Rust

The ownership rules that prevent dangling pointers also prevent data races: the compiler rejects code that shares mutable data between threads without synchronization.

Threads

use std::thread;

fn main() {
    let name = String::from("worker");
    let handle = thread::spawn(move || {          // move: the thread owns `name`
        println!("hello from {name}");
        42
    });
    let result = handle.join().unwrap();          // wait; get the return value
    println!("{result}");
}

spawn requires the closure to own everything it uses, because the thread may outlive the function. Borrowing a local is rejected:

use std::thread;

fn main() {
    let mut count = 0;
    let h = thread::spawn(|| count += 1);   // error[E0373]: closure may outlive the current function
    h.join().unwrap();
}

Mutex: the lock owns the data

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));         // data lives inside the Mutex
    let mut handles = Vec::new();

    for _ in 0..4 {
        let c = Arc::clone(&counter);              // another owner (reference-counted)
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *c.lock().unwrap() += 1;           // lock, modify, unlock when the guard drops
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());      // 4000
}
  • Mutex<T> contains the T. The only way to reach it is lock(), which returns a guard; the lock is released when the guard is dropped (chapter 11). You cannot forget to unlock, and cannot touch the data without locking.
  • Arc<T> is an atomically reference-counted shared pointer, the safe version of “several threads hold a pointer, the last one frees it”.

Send and Sync: the compiler’s data-race check

Two marker traits, derived automatically:

  • T: Send means a value of T may be moved to another thread.
  • T: Sync means &T may be shared between threads.

Non-thread-safe types opt out, and spawn requires Send:

use std::rc::Rc;
use std::thread;

fn main() {
    let rc = Rc::new(5);                            // non-atomic refcount
    thread::spawn(move || println!("{rc}"));        // error[E0277]: `Rc<i32>` cannot be sent between threads safely
}

Rc uses a plain integer counter, which would race, so it is not Send; Arc is. Likewise RefCell is not Sync; Mutex is.

Scoped threads: borrowing across threads

thread::scope guarantees all threads finish before it returns, so they may borrow local data safely:

use std::thread;

fn main() {
    let v = vec![1, 2, 3, 4, 5, 6];
    let (a, b) = v.split_at(3);
    let (x, y) = thread::scope(|s| {
        let h1 = s.spawn(|| a.iter().sum::<i32>());
        let h2 = s.spawn(|| b.iter().sum::<i32>());
        (h1.join().unwrap(), h2.join().unwrap())
    });
    println!("{x} {y}");                            // 6 15
}

Atomics

For a single shared integer, an atomic is lighter than a mutex. The orderings are the same as C11’s memory_order:

use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

static HITS: AtomicUsize = AtomicUsize::new(0);

fn main() {
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..1000 {
                    HITS.fetch_add(1, Ordering::Relaxed);
                }
            });
        }
    });
    println!("{}", HITS.load(Ordering::SeqCst));    // 4000
}

Channels: message passing

Instead of sharing memory, send values between threads. Sending moves the value, so the sender cannot keep using it:

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();               // multiple producers, one consumer
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(id * 10).unwrap();
        });
    }
    drop(tx);                                      // close our own sender, or the loop never ends

    let mut got: Vec<i32> = rx.iter().collect();   // ends when all senders are gone
    got.sort();
    println!("{got:?}");                           // [0, 10, 20]
}

async and await

Threads are not the only way to wait for many things at once. An async fn returns a future: a value describing a computation that has not run yet, compiled into a state machine, much like the hand-written one a C event loop uses. .await pauses the function until the awaited future is ready. Nothing runs until something polls the future, and the standard library ships no scheduler: a crate such as tokio provides one. To show there is no magic, here is a complete executor for futures that never block:

use std::future::Future;
use std::pin::pin;
use std::task::{Context, Poll, Waker};

async fn add(a: i32, b: i32) -> i32 {
    a + b
}

async fn sum() -> i32 {
    add(1, 2).await + add(3, 4).await
}

fn block_on<F: Future>(f: F) -> F::Output {
    let mut f = pin!(f);                       // a future must not move once polled
    let mut cx = Context::from_waker(Waker::noop());
    loop {
        if let Poll::Ready(v) = f.as_mut().poll(&mut cx) {
            return v;
        }
    }
}

fn main() {
    println!("{}", block_on(sum()));          // 10
}

pin! fixes the future in place, because a state machine may hold pointers into itself; that is what the standard library’s Pin type guarantees. A real executor also parks the thread until a Waker says the future can make progress, instead of spinning as this one does. Use async for programs with very many mostly idle connections; ordinary threads (this chapter) are simpler and enough for most work.

Under the hood

  • thread::spawn creates an OS thread (pthread_create on Linux). There is no green-thread runtime in std; async runtimes are separate libraries.
  • A Mutex is a futex or pthread mutex plus a poisoned flag, which is set if a thread panics while holding the lock (lock() then returns an Err).
  • Send and Sync have no runtime representation. They are checked at compile time and prevent most data races. They do not prevent deadlocks or logical races such as lock-order inversion.
  • Arc bumps its counter with an atomic add on clone and drops the value when the last owner goes away; Rc does the same non-atomically and is cheaper.

C habits to unlearn

  • Do not share a global and “remember” to lock it. Put it inside a Mutex.
  • Do not use Relaxed ordering unless you can explain it.
  • Do not hold a guard longer than needed; scope it with a block.
  • Prefer channels or scoped threads over Arc<Mutex<_>> when the data flow allows.

Solutions

1. Without move the closure borrows a local variable, and the thread may outlive that variable’s scope: error[E0373]: closure may outlive the current function, but it borrows .... The fix is move, which hands the value to the thread. In C you would pass a pointer to a stack variable to pthread_create and hope the function does not return first.

2.

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;
use std::thread;

fn main() {
    let count = Arc::new(AtomicUsize::new(0));
    let hs: Vec<_> = (0..4)
        .map(|_| {
            let count = Arc::clone(&count);
            thread::spawn(move || {
                for _ in 0..1000 {
                    count.fetch_add(1, Ordering::Relaxed);
                }
            })
        })
        .collect();
    for h in hs {
        h.join().unwrap();
    }
    println!("{}", count.load(Ordering::Relaxed));   // 4000
}

There is no lock and no guard to hold. An atomic suits a single counter. A Mutex is needed once several values must change together.

3.

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    let producer = thread::spawn(move || {
        for i in 1..=5 {
            tx.send(i).unwrap();
        }
    });                               // tx is dropped here, which closes the channel
    let sum: i32 = rx.iter().sum();   // ends when the channel closes
    producer.join().unwrap();
    println!("{sum}");                // 15
}

4.

use std::thread;

fn parallel_sum(mut data: Vec<u32>) -> u32 {
    let right = data.split_off(data.len() / 2);
    let h1 = thread::spawn(move || data.iter().sum::<u32>());
    let h2 = thread::spawn(move || right.iter().sum::<u32>());
    h1.join().unwrap() + h2.join().unwrap()
}

fn main() {
    let data: Vec<u32> = (1..=100).collect();
    assert_eq!(parallel_sum(data), 5050);
    println!("ok");
}

Each half is moved into its thread, so there is no shared data and no lock.

use std::future::Future;

async fn add(a: i32, b: i32) -> i32 {
