Rust for C Programmers

Errors, panics, testing and tooling

In C

Recoverable errors are return codes, fatal ones call abort() or exit(), and some programs use setjmp/longjmp. Tests are a separate harness; diagnostics come from -Wall, sanitizers, Valgrind and clang-tidy.

if (!(p = malloc(n))) { fprintf(stderr, "oom\n"); exit(1); }
assert(i < len);          /* compiled out with -DNDEBUG */

In Rust

Two kinds of failure, kept apart:

MeaningMechanism
recoverable (file missing, bad input)expected, handle itResult and ? (chapter 14)
bug (index out of range, broken invariant)should never happenpanic!

Panics

A panic prints a message and by default unwinds: it runs Drop for live locals (chapter 11) and ends the thread. In main, that ends the program with exit code 101.

fn main() {
    let v = vec![1, 2, 3];
    let i = 7;
    println!("about to fail");
    println!("{}", v[i]);       // panics: index out of bounds: the len is 3 but the index is 7
}

Set RUST_BACKTRACE=1 to see the stack. unwrap(), expect(), assert!, unreachable!() and integer overflow in debug builds are all panics.

A panic is not an exception to catch for control flow, but catch_unwind can stop one at a boundary (a thread pool, an FFI entry):

use std::panic;

fn main() {
    let r = panic::catch_unwind(|| {
        let v = vec![1];
        v[5]
    });
    println!("{}", r.is_err());     // true
}

To make panics abort immediately (smaller binaries, no unwinding tables, and what embedded targets usually want), put this in Cargo.toml:

[profile.release]
panic = "abort"

Exit codes

use std::process::ExitCode;

fn main() -> ExitCode {
    if std::env::args().count() > 5 {
        eprintln!("too many arguments");
        return ExitCode::from(2);
    }
    ExitCode::SUCCESS
}

main may also return a Result (chapter 14). A returned Err prints it and exits with 1.

Testing is built in

Put tests next to the code. cargo test builds them and runs them in parallel:

pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]                       // compiled only for `cargo test`
mod tests {
    use super::*;

    #[test]
    fn adds() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    #[should_panic(expected = "overflow")]
    fn overflows() {
        let _ = add(i32::MAX, 1);   // panics in a debug build
    }

    #[test]
    fn works_with_result() -> Result<(), String> {
        let n: i32 = "12".parse().map_err(|e| format!("{e}"))?;
        assert_eq!(n, 12);
        Ok(())
    }
}
  • tests/ directory: integration tests that use your crate like an outside user.
  • Doc-tests: code blocks in /// comments are compiled and run. This book’s snippets are checked the same way by mdbook test.
  • assert!, assert_eq!, assert_ne! always run; debug_assert! only in debug builds.

Typical workflow:

cargo fmt            # format
cargo clippy         # lint
cargo test           # unit, integration and doc tests
cargo build --release
cargo +nightly miri test   # if the crate has unsafe

Build profiles

The C -O0 -g / -O2 choice becomes profiles in Cargo.toml:

[profile.release]
opt-level = 3          # or "s"/"z" for size
lto = true             # whole-program optimization, like -flto
codegen-units = 1
overflow-checks = false
debug = false

[profile.dev]
opt-level = 1          # make debug builds less slow

Under the hood

  • Unwinding uses the same tables as C++ exceptions (.eh_frame), which is why panic = "abort" shrinks the binary.
  • Test functions are collected by the compiler and run by a generated harness; no registration code is needed.
  • Result-based error handling has no unwinding cost on the success path: it is a branch on a returned tag.
  • Overflow checks and bounds checks are the debug-mode “sanitizers” that C programmers add with -fsanitize=undefined; they are on by default.

C habits to unlearn

  • Do not exit() from deep inside a library. Return an error and let main decide.
  • Do not use assert for input validation (it vanishes with NDEBUG); validate and return Result.
  • Do not skip clippy; it catches C-isms such as manual index loops.
  • Do not write a separate test harness; use #[test].

Exercises

  1. Write a function parse_port(&str) -> Result<u16, String> and tests for good, empty and out-of-range input.

  2. Run a failing test with RUST_BACKTRACE=1 cargo test -- --nocapture.

  3. Add #![warn(clippy::pedantic)] to a crate and fix three lints.

  4. Complete the code. Parse a percentage such as "50%".

    fn parse_percent(s: &str) -> Result<u8, String> {
    todo!("strip the % suffix, parse as u8, reject values above 100")
}

fn main() {

    assert!(parse_percent("101%").is_err());
    assert!(parse_percent("x%").is_err());
    assert!(parse_percent("50").is_err());

  5. Write and test. Write fn average(v: &[i32]) -> i32 that panics on an empty slice, with a #[should_panic] test for that case, and a second test that returns a Result.

Solutions

1.

fn parse_port(s: &str) -> Result<u16, String> {
    if s.is_empty() {
        return Err("empty".to_string());
    }
    s.parse::<u16>().map_err(|e| format!("bad port {s:?}: {e}"))
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn good() {
        assert_eq!(parse_port("8080"), Ok(8080));
    }

    #[test]
    fn empty() {
        assert_eq!(parse_port(""), Err("empty".to_string()));
    }

    #[test]
    fn out_of_range() {
        assert!(parse_port("70000").is_err());   // u16 holds up to 65535
    }
}

fn main() {
    println!("{:?}", parse_port("8080"));
}

Run it with cargo test. Note that 70000 is rejected by the u16 parse itself, so the range check needs no extra code.

2. RUST_BACKTRACE=1 prints the call stack at the panic. -- --nocapture stops the test harness from swallowing println! output (by default it shows output only for tests that fail). Use both when a test fails and you need to see what led to it.

3. On the capstone crate, clippy::pedantic reports must_use_candidate (a function whose result should not be ignored) and iter_without_into_iter (an iter method without a matching IntoIterator impl for &List). Others you are likely to meet are missing_errors_doc and cast_possible_truncation. Pedantic lints are opinionated: fix the ones that improve the code and #[allow(...)] the rest with a comment.

4.

fn parse_percent(s: &str) -> Result<u8, String> {
    let digits = s.strip_suffix('%').ok_or("missing %")?;
    let n: u8 = digits.parse().map_err(|e| format!("bad number: {e}"))?;
    if n > 100 {
        return Err(format!("{n} is above 100"));
    }
    Ok(n)
}

fn main() {
    assert_eq!(parse_percent("50%"), Ok(50));
    assert!(parse_percent("101%").is_err());
    assert!(parse_percent("x%").is_err());
    assert!(parse_percent("50").is_err());
    println!("ok");
}

5.

fn average(v: &[i32]) -> i32 {
    assert!(!v.is_empty(), "average of an empty slice");
    v.iter().sum::<i32>() / v.len() as i32
}

fn main() {
    println!("{}", average(&[2, 4]));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    #[should_panic(expected = "empty slice")]
    fn empty_panics() {
        average(&[]);
    }

    #[test]
    fn returns_result() -> Result<(), String> {
        if average(&[2, 4]) == 3 {
            Ok(())
        } else {
            Err("wrong average".to_string())
        }
    }
}

#[should_panic] checks that the failure path really fails, like a C test that expects abort(). A test that returns Result can use ?.
