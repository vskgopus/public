How it works

This book teaches Rust to people who already know C well. Every concept is explained by pointing at the C pattern you already use, showing the hazard that pattern carries, and then showing what Rust does instead.

You do not need to install anything to start. Each Rust snippet has a Run button (and, when editable, you can change it first). Output comes from the Rust Playground.

Here is the smallest comparison:

#include <stdio.h>

int main(void) {
    printf("Hello, world!\n");
    return 0;
}

fn main() {
    println!("Hello, world!");
}

Toolchain: cargo vs cc/make

In C

You compile each .c file (a translation unit) to an object file, then link the objects into a program. A Makefile or CMake file describes the steps, and you manage dependencies and flags yourself.

cc -std=c11 -Wall -Wextra -O2 -c main.c -o main.o
cc main.o util.o -o app

In Rust

The unit of compilation is a crate, not a file. A crate is a whole tree of modules, starting at one root file (main.rs for a program, lib.rs for a library), compiled in a single rustc invocation. Cargo is the build system, package manager and test runner in one.

cargo new hello        # creates Cargo.toml and src/main.rs
cd hello
cargo run              # build (debug) and run
cargo build --release  # optimized build, like -O2
cargo test             # run the tests
cargo check            # type-check only: fast, no binary

Cargo.toml plays the role of the Makefile, with dependencies built in:

[package]
name = "hello"
version = "0.1.0"
edition = "2024"

[dependencies]
# libc = "0.2"   # a dependency is one line, no manual download or linking

The program is the same as in the introduction. Run it:

fn main() {
    println!("Hello, world!");
}

Under the hood

  • rustc uses LLVM, the same backend as clang. Optimized Rust and C can produce very similar machine code. Try both on Compiler Explorer.
  • A debug build is unoptimized and keeps runtime checks (overflow, array bounds). A release build removes the overflow checks by default but keeps bounds checks.
  • Editions (2015, 2018, 2021, 2024) are like -std= versions, but crates of different editions link together freely.
  • The standard library is split in three layers: core (no OS, no heap), alloc (heap types) and std (OS services). std is roughly “libc plus containers”. Chapter 23 returns to this.

C habits to unlearn

  • There is no separate declaration step. Order of definitions does not matter inside a crate, so no prototypes are needed.
  • You do not write -Wall. The compiler is strict by default, and “it compiles” means much more than in C.
  • Do not look for #include. Everything in std that you commonly need is in the prelude; the rest comes in with use.

Exercises

  1. Run cargo new hello and cargo run. Then add let unused = 5; to main and read the warning.
  2. Compare cargo build and cargo build --release: where do the binaries go, and how big are they?
  3. Paste the hello program into Compiler Explorer next to the C version and compare the generated code.
Solutions

1. The build prints a warning, and the program still runs:

warning: unused variable: `unused`
 --> src/main.rs:2:9
  |
2 |     let unused = 5;
  |         ^^^^^^ help: if this is intentional, prefix it with an underscore: `_unused`

C needs -Wall for the same diagnostic. Cargo turns the useful warnings on by default. Rename the variable to _unused and the warning goes away.

2. cargo build writes target/debug/hello; cargo build --release writes target/release/hello. On one Linux x86-64 machine with rustc 1.100 the sizes were about 4.5 MB (debug) and 445 KB (release). Your numbers will differ. The debug binary is bigger because it has no optimization and carries debug info, like gcc -O0 -g against gcc -O2.

3. Expect the same shape of code for plain arithmetic at -O. Differences you may see: Rust’s println! expands to a call into the standard library’s formatting machinery instead of printf, and a debug build keeps the overflow checks that release removes (chapter 3).

Variables and mutability

In C

Variables are mutable unless you add const. Locals are uninitialized unless you assign them, and reading one is undefined behavior. Globals are zero initialized. Names can shadow in inner scopes only.

int x = 5;
x = 6;                    /* fine */
const int y = 7;          /* y = 8; is an error */
int z;                    /* indeterminate value; reading it is UB */
static int counter;       /* file-scope, zero-initialized */
#define LIMIT 100         /* a macro, not a variable */

In Rust

Bindings are immutable by default; you opt in to mutation with mut. The compiler refuses to read a variable before it is assigned on every path.

fn main() {
    let x = 5;          // immutable, type inferred (i32)
    let mut y = 6;      // mutable
    y += 1;
    let z: u8;          // declared, not yet initialized
    z = 9;              // assigned exactly once: fine
    println!("{x} {y} {z}");
}

Mutating an immutable binding is rejected:

fn main() {
    let x = 5;
    x = 6; // error[E0384]: cannot assign twice to immutable variable
    println!("{x}");
}

So is reading before initialization, which in C is silent UB:

fn main() {
    let z: i32;
    println!("{z}"); // error[E0381]: used binding `z` isn't initialized
}

Shadowing

A new let with the same name creates a new variable that hides the old one. It can even change the type, which mut cannot do.

fn main() {
    let spaces = "   ";          // &str
    let spaces = spaces.len();   // usize: a new variable, same name
    println!("{spaces}");
    {
        let spaces = 100;        // shadows only inside this block
        println!("{spaces}");
    }
    println!("{spaces}");        // back to 3
}

const and static

const LIMIT: u32 = 100;              // like #define / enum constant, but typed
static GREETING: &str = "hello";     // one fixed address for the whole program

fn main() {
    println!("{LIMIT} {GREETING}");
}
  • const is inlined at each use; it has no address. Its type is required and its value must be computable at compile time. It replaces most #define constants, with a type.
  • static is a single object with a fixed address, like a C global.
  • static mut is a mutable global. Every access needs unsafe, because nothing prevents data races:
static mut COUNTER: u32 = 0;

fn main() {
    unsafe { COUNTER += 1; }
    let seen = unsafe { COUNTER }; // copy the value out
    println!("{seen}");
}

Prefer atomics or a Mutex for shared state (chapter 22); static mut is shown only so you can recognize it.

Under the hood

  • let bindings are stack slots (or registers), exactly like C locals. Immutability is a compile-time rule only; it costs nothing at runtime.
  • Shadowing creates a separate variable; the old value still lives until the end of its scope.
  • Names are snake_case for variables and functions, SCREAMING_SNAKE_CASE for const and static. The compiler warns if you deviate.

C habits to unlearn

  • Don’t declare variables at the top of a function. Declare them where they are first given a value.
  • Don’t reach for mut by reflex. Start immutable and add mut when the compiler asks; it documents which values change.
  • Don’t use globals for convenience. Shared mutable state needs explicit synchronization in Rust.

Exercises

  1. Remove mut from y in the first example and read the error.
  2. Make spaces change type without shadowing, using let mut. What does the compiler say?
  3. Replace a #define BUF_SIZE 256 with a const and use it as an array length: [0u8; BUF_SIZE].
Solutions

1. The compiler stops with error[E0384]: cannot assign twice to immutable variable, and its help text suggests let mut y. Rust’s default is the reverse of C: a binding is const unless you ask otherwise.

2. Without shadowing, a binding keeps its type:

fn main() {
    let mut spaces = "   ";
    spaces = spaces.len();   // error[E0308]: mismatched types: expected `&str`, found `usize`
}

Shadowing makes a new variable that may have a new type: let spaces = spaces.len();.

3.

const BUF_SIZE: usize = 256;

fn main() {
    let buf = [0u8; BUF_SIZE];
    println!("{}", buf.len());   // 256
}

Primitive types

In C

Integer sizes depend on the platform (int, long), conversions happen silently, signed overflow is undefined behavior, and char is a byte of unspecified signedness.

#include <stdint.h>
uint8_t  a = 300;      /* silently becomes 44 */
int      b = -1;
unsigned c = b;        /* silently becomes 4294967295 */
int      d = 3.99;     /* silently becomes 3 */
/* INT_MAX + 1 is undefined behavior */

In Rust

Sizes are in the type name, there are no implicit conversions, and overflow has defined behavior.

fn main() {

    let hex = 0xff;
    let bin = 0b1010_0101;
    let byte = b'A';          // u8 literal, 65
    let f = 2.5;              // default f64
    let big: u64 = 5_000_000_000;
    let n: usize = 10;        // array lengths and indexes are usize
    println!("{a} {hex} {bin} {byte} {f} {big} {n}");
}

No implicit conversions

fn main() {
    let a: i32 = 5;
    let b: i64 = a; // error[E0308]: mismatched types
    println!("{b}");
}

Convert explicitly. Use From/into when the conversion cannot lose data, and TryFrom when it can fail. Use as when you want C-style truncation:

fn main() {
    let a: i32 = 5;
    let wide: i64 = a.into();                  // lossless: always allowed
    let narrow = u8::try_from(300_i32);        // Err: 300 doesn't fit
    println!("{wide} {narrow:?}");

    // `as` is like a C cast: it truncates and never fails.
    println!("{}", 300_i32 as u8);             // 44
    println!("{}", -1_i32 as u32);             // 4294967295
    println!("{}", 3.99_f64 as i32);           // 3 (rounds toward zero)
    println!("{}", f64::NAN as i32);           // 0 (defined, unlike C)
    println!("{}", 1e20_f64 as i32);           // 2147483647 (saturates)
}

Overflow is defined

In a debug build, + - * that overflow panic. In a release build they wrap (two’s complement). Neither is undefined behavior. When you mean a specific behavior, say so:

fn main() {
    let x: u8 = 250;
    println!("{}", x.wrapping_add(10));          // 4      (modular, like unsigned C)
    println!("{:?}", x.checked_add(10));         // None   (overflow reported)
    println!("{}", x.saturating_add(10));        // 255    (clamped)
    println!("{:?}", x.overflowing_add(10));     // (4, true)
}

Integer division or remainder by zero panics, as does i32::MIN / -1.

bool and char

use std::mem::size_of;

fn main() {
    println!("{}", size_of::<bool>());   // 1
    println!("{}", size_of::<char>());   // 4: a Unicode code point
    println!("{}", size_of::<usize>());  // pointer width: 8 on 64-bit
    let c = 'é';                         // a char, in single quotes
    println!("{} {}", c, c as u32);      // é 233
}

An if condition must be a real bool; an integer is not accepted (next chapters).

Under the hood

  • i32, u64 etc. have exactly the size in their name on every platform. Only isize/usize follow the pointer width, like intptr_t/size_t.
  • Signed integers are two’s complement. Overflow checks in debug builds are inserted by the compiler; cargo build --release turns them off (it can be re-enabled with overflow-checks = true in the profile).
  • Floats follow IEEE 754. f64 as i32 saturates and maps NaN to 0, so it has no undefined behavior.
  • bool is one byte that is always 0 or 1; any other bit pattern is undefined.

C habits to unlearn

  • Do not rely on int being 32 bits or char being signed. Pick the exact type.
  • Use usize for indexes and lengths, and convert other integers explicitly.
  • Prefer try_from over as when truncation would be a bug.
  • A Rust char is not a byte. Use u8 for bytes and b'x' for byte literals.

Exercises

  1. What does (-7i32).rem_euclid(3) print, and how does it differ from -7 % 3?
  2. Call 255u8.checked_add(1), .wrapping_add(1) and .saturating_add(1).
  3. Try let x: u32 = -1; and read the error. How do you write the C result?
Solutions

1. (-7i32).rem_euclid(3) is 2. -7 % 3 is -1. The % operator takes the sign of the dividend, as C99 does, while rem_euclid always returns a result in 0..3.

fn main() {
    assert_eq!((-7i32).rem_euclid(3), 2);
    assert_eq!(-7 % 3, -1);
}

2.

fn main() {
    println!("{:?}", 255u8.checked_add(1));    // None
    println!("{}", 255u8.wrapping_add(1));     // 0
    println!("{}", 255u8.saturating_add(1));   // 255
}

3. A negative literal does not fit an unsigned type, and the compiler says so:

fn main() {
    let x: u32 = -1;   // error[E0600]: cannot apply unary operator `-` to type `u32`
}

The C result (all bits set) is written out explicitly: u32::MAX, !0u32, or -1i32 as u32.

Functions and expressions

In C

Statements and expressions are distinct. A function returns with return, may have out-parameters through pointers, must be declared before use, and can be variadic.

int add(int a, int b) { return a + b; }

void divmod(int a, int b, int *q, int *r) {   /* out-parameters */
    *q = a / b;
    *r = a % b;
}

In Rust

Functions use fn, with the parameter types after the names and the return type after ->. Almost everything is an expression, and a block evaluates to its last expression when that expression has no trailing semicolon.

fn add(a: i32, b: i32) -> i32 {
    a + b            // no semicolon: this is the return value
}

fn main() {
    println!("{}", add(2, 3));
}

A semicolon turns an expression into a statement whose value is (). This is a classic first error:

#![allow(unused)]
fn main() {
fn add(a: i32, b: i32) -> i32 {
    a + b;           // error[E0308]: mismatched types: expected i32, found ()
}
}

return still exists, for early exits:

fn sign(x: i32) -> i32 {
    if x < 0 {
        return -1;
    }
    if x == 0 { 0 } else { 1 }   // `if` is an expression
}

fn main() {
    println!("{} {} {}", sign(-5), sign(0), sign(9));
}

Blocks, if and match are expressions

fn main() {
    let n = 7;
    let kind = if n % 2 == 0 { "even" } else { "odd" };   // like C's ?:
    let squared = {
        let t = n * n;
        t + 0                                             // value of the block
    };
    println!("{kind} {squared}");
}

Returning several values: tuples instead of out-pointers

fn divmod(a: i32, b: i32) -> (i32, i32) {
    (a / b, a % b)
}

fn main() {
    let (q, r) = divmod(17, 5);       // destructure the tuple
    println!("{q} {r}");              // 3 2
}

The unit type () and the never type !

  • A function without -> returns (), the “empty tuple”. It is the closest thing to void, but it is a real type with a single value.
  • A function that never returns has the type ! (like noreturn/abort):
fn fail(msg: &str) -> ! {
    panic!("fatal: {msg}");
}

fn parse_or_die(s: &str) -> i32 {
    match s.parse::<i32>() {
        Ok(v) => v,
        Err(_) => fail("not a number"),   // `!` fits any type
    }
}

fn main() {
    println!("{}", parse_or_die("42"));
}

fn double(x: i32) -> i32 { x * 2 }

fn main() {

Under the hood

  • Parameters are passed by value following the platform ABI, like C. Rust has its own ABI for fn by default and does not promise a stable one. Use extern "C" fn when C must call it (chapter 21).
  • Passing a non-Copy value moves it. The caller can no longer use it. This replaces C’s “who frees this?” convention (chapter 7).
  • There is no function overloading and no default arguments; use different names, Option parameters, or a struct of options.
  • Recursion works as in C, but Rust does not guarantee tail-call elimination.

C habits to unlearn

  • Do not add ; after the final value expression. Do not write return at the end of every function.
  • Do not use out-parameters for multiple results. Return a tuple or struct.
  • Do not look for prototypes. Put main first or last as you like.

Control flow

In C

if (x) { ... } else { ... }                 /* any non-zero value is true */
for (int i = 0; i < n; i++) { ... }
while (cond) { ... }
do { ... } while (cond);
switch (x) { case 1: ...; /* falls through */ case 2: ...; break; default: ...; }
goto cleanup;

In Rust

if

The condition must be a bool. Parentheses are not needed, but braces are required. if is an expression.

fn main() {
    let x = 3;
    if x > 0 {
        println!("positive");
    } else if x < 0 {
        println!("negative");
    } else {
        println!("zero");
    }
}
fn main() {
    let x = 3;
    if x {          // error[E0308]: expected `bool`, found integer
        println!("yes");
    }
}

Loops

Rust has three: loop (infinite), while, and for. There is no C-style three-part for and no do/while.

fn main() {
    // loop: infinite; `break` can carry a value
    let mut tries = 0;
    let found = loop {
        tries += 1;
        if tries == 4 {
            break tries * 10;       // the loop evaluates to 40
        }
    };
    println!("{found}");

    // while
    let mut n = 3;
    while n > 0 {
        n -= 1;
    }

    // do { } while (cond)  ==  loop with a break at the end
    let mut k = 0;
    loop {
        k += 1;
        if k >= 3 { break; }
    }
}

for iterates over an iterator. Ranges are the equivalent of counting loops, and they cannot go out of bounds or off by one into an uninitialized index:

fn main() {
    for i in 0..3 {            // 0, 1, 2   (end excluded)
        print!("{i} ");
    }
    for i in 0..=3 {           // 0, 1, 2, 3 (end included)
        print!("{i} ");
    }
    for i in (0..3).rev() {    // 2, 1, 0
        print!("{i} ");
    }
    for i in (0..10).step_by(4) { // 0, 4, 8
        print!("{i} ");
    }
    println!();

    let a = [10, 20, 30];
    for x in a {               // by value (arrays of Copy types)
        print!("{x} ");
    }
    for (i, x) in a.iter().enumerate() {   // index and element together
        print!("[{i}]={x} ");
    }
    println!();
}

C’s for (i = 0; i <= n; i++) is for i in 0..=n. There is no way to write the classic off-by-one past the end by accident; and iterating the elements directly needs no index at all.

Labels

break and continue can target an outer loop by label, replacing most uses of goto and flag variables:

fn main() {
    'outer: for i in 0..5 {
        for j in 0..5 {
            if i * j == 6 {
                println!("found {i} {j}");
                break 'outer;
            }
        }
    }
}

match: a safer switch

match compares a value against patterns. It has no fall-through (no break needed) and must be exhaustive: the compiler rejects a missing case.

fn describe(n: i32) -> &'static str {
    match n {
        0 => "zero",
        1 | 2 | 3 => "small",          // several values
        4..=9 => "medium",             // a range
        x if x < 0 => "negative",      // a guard
        _ => "large",                  // `_` is `default`
    }
}

fn main() {
    for n in [0, 2, 5, -4, 100] {
        println!("{n}: {}", describe(n));
    }
}

Forget a case and it will not compile:

fn main() {
    let n: u8 = 3;
    let s = match n {
        0 => "zero",
        1 => "one",
        // error[E0004]: non-exhaustive patterns: `2_u8..=u8::MAX` not covered
    };
    println!("{s}");
}

Patterns can also bind parts of the value, which is where match becomes far more powerful than switch (chapters 6 and 14).

Compound types

In C

Aggregates are arrays, struct and union. An array decays to a pointer and loses its length, a union does not remember which member is live, and an enum is just named integers.

struct point { int x, y; };

enum shape_kind { CIRCLE, RECT };
struct shape {
    enum shape_kind kind;          /* the "tag", kept by hand */
    union {
        struct { double r; } circle;
        struct { double w, h; } rect;
    } u;
};

In Rust

Tuples

fn main() {
    let t: (i32, f64, char) = (1, 2.5, 'x');
    println!("{} {} {}", t.0, t.1, t.2);       // fields by position
    let (a, b, c) = t;                          // destructuring
    println!("{a} {b} {c}");
}

Arrays

[T; N] is a fixed-size array value. The length is part of the type. It does not decay to a pointer, and indexing is bounds checked.

fn main() {
    let a = [1, 2, 3, 4, 5];       // [i32; 5]
    let zeros = [0u8; 16];         // 16 zero bytes, like `uint8_t z[16] = {0};`
    println!("{} {}", a.len(), zeros.len());

    let i = std::hint::black_box(7);  // hides the constant, so the check happens at run time
    // a[i] panics at run time: "index out of bounds: the len is 5 but the index is 7"
    // In C this reads past the end: undefined behavior.
    if i < a.len() {
        println!("{}", a[i]);
    }
    println!("{:?}", a.get(i));    // None: a checked access, no panic
}

Slices: pointer plus length

A slice &[T] is a view into part of an array or vector. It is a fat pointer: an address and a length, the pair that C programs pass by hand as (int *a, size_t n).

use std::mem::size_of;

fn sum(xs: &[i32]) -> i32 {        // C: int sum(const int *xs, size_t n)
    let mut total = 0;
    for x in xs {
        total += x;
    }
    total
}

fn main() {
    let a = [1, 2, 3, 4, 5];
    println!("{}", sum(&a));        // whole array
    println!("{}", sum(&a[1..4]));  // elements 1, 2, 3 -> 9
    println!("{}", size_of::<&[i32]>() == 2 * size_of::<usize>()); // true
}

A slice carries its length, so functions cannot walk past the end without the check noticing.

Structs

struct Point {
    x: i32,
    y: i32,
}

struct Meters(f64);      // tuple struct: a named wrapper
struct Marker;           // unit struct: no data

    let mut p = Point { x: 1, y: 2 };

}

There is no designated-initializer shorthand with omitted fields: every field must be given, so there are no uninitialized members.

Enums: tagged unions done right

A Rust enum is a sum type: each variant may carry data, and the compiler tracks which variant is live. This is the struct { tag; union } pattern from C, built in and checked.

enum Shape {
    Circle { r: f64 },
    Rect { w: f64, h: f64 },
    Point,
}

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Circle { r } => 3.14159 * *r * *r,
        Shape::Rect { w, h } => w * h,
        Shape::Point => 0.0,
    }
}

fn main() {
    let shapes = [Shape::Circle { r: 1.0 }, Shape::Rect { w: 2.0, h: 3.0 }, Shape::Point];
    for s in &shapes {
        println!("{}", area(s));
    }
}

You cannot read the wrong union member: the only way to the data is match, which also forces you to handle every variant. Adding a variant makes every non-exhaustive match fail to compile.

Plain C-like enums are available too, with explicit values:

#[derive(Debug, Clone, Copy)]
enum Color {
    Red = 1,
    Green = 2,
    Blue = 4,
}

fn main() {
    println!("{} {:?}", Color::Blue as i32, Color::Green);   // 4 Green
}

Unlike C, Color is its own type: an arbitrary integer is not a Color.

  • Do not cast between an integer and an enum; use as to get the number and a match or TryFrom for the reverse.

Ownership and moves

In C

Heap memory has no owner in the language. By convention, someone must call free exactly once, and nobody may touch the memory afterwards. Nothing checks this.

char *a = malloc(6);
strcpy(a, "hello");
char *b = a;           /* two pointers, one block: who frees it? */
free(a);
free(b);               /* double free: undefined behavior */
printf("%s", a);       /* use after free: undefined behavior */

Most C bugs that become security holes are ownership mistakes: double free, use after free, leaks, and freeing the wrong pointer.

In Rust

Every value has exactly one owner: a variable. When the owner goes out of scope the value is dropped (freed). Assigning or passing a value to another variable moves ownership; the old name becomes unusable.

fn main() {
    let a = String::from("hello");   // a owns a heap buffer
    let b = a;                        // ownership moves to b
    println!("{b}");
}   // b goes out of scope: the buffer is freed, once

Using the old owner is a compile error, not a runtime bug:

fn main() {
    let a = String::from("hello");
    let b = a;
    println!("{a}");   // error[E0382]: borrow of moved value: `a`
    println!("{b}");
}

This one rule removes double free (only one owner frees), use after free (the old name is dead), and most leaks (the owner frees automatically).

Moves into and out of functions

fn consume(s: String) {
    println!("got {s}");
}   // s dropped here

fn pass_through(s: String) -> String {
    s                           // ownership returned to the caller
}

fn main() {
    let a = String::from("x");
    let a = pass_through(a);     // moved in, moved back out
    consume(a);                  // moved in for good
    // a is unusable here
}

Passing a value to a function is a move, just like assignment. To let a function look at a value without taking it, you borrow it (next chapter).

Cloning: an explicit deep copy

If you really want two independent owners, say so with .clone(). It is a visible allocation and copy, never silent:

fn main() {
    let a = String::from("hello");
    let b = a.clone();         // new heap buffer, same contents
    println!("{a} {b}");       // both valid
}

Copy types: plain data is copied, not moved

Types that are just bits (integers, floats, bool, char, tuples and arrays of those, shared references) implement Copy. They are copied on assignment, like in C, and the original stays usable.

fn main() {
    let x = 5;
    let y = x;               // copied
    println!("{x} {y}");     // both fine
}

A type that owns a resource (heap memory, a file) can never be Copy.

Partial moves and Box

Box<T> is the simplest owner: one heap allocation, like T *p = malloc(sizeof *p) with an automatic free.

fn main() {
    let b = Box::new(41);       // heap-allocated i32
    let c = *b + 1;             // dereference with *, like C
    println!("{c}");
}   // heap block freed here

Borrowing

In C

You share data by passing pointers. const T * promises not to modify through that pointer, but other pointers may still modify the same object, and nothing stops a pointer from dangling or being NULL.

void push(struct vec *v, int x);

int *first = &v.data[0];
push(&v, 4);            /* may realloc: `first` now dangles */
printf("%d", *first);   /* undefined behavior */

This is iterator invalidation, and it is only one form of aliasing bug.

In Rust

A reference borrows a value without owning it. There are two kinds:

SyntaxAllowed at once
shared (read-only)&Tany number
exclusive (mutable)&mut Texactly one, and no &T alongside

The rule is aliasing XOR mutability: a value may have many readers or one writer, never both. The compiler checks it.

fn length(s: &String) -> usize {   // borrows: does not take ownership
    s.len()
}

fn shout(s: &mut String) {         // exclusive borrow: may modify
    s.push('!');
}

fn main() {
    let mut s = String::from("hi");
    println!("{}", length(&s));    // lend it read-only
    shout(&mut s);                 // lend it mutably
    println!("{s}");               // the owner still has it: "hi!"
}

References are always valid and never null. You use them with . and, to read the value itself, * (the compiler adds * automatically for method calls and fields).

fn inc(x: &mut i32) {
    *x += 1;                       // explicit dereference, like C
}

fn main() {
    let mut n = 1;
    inc(&mut n);
    println!("{n}");               // 2
}

The C bug above, rejected at compile time

fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];             // shared borrow of v
    v.push(4);                     // error[E0502]: cannot borrow `v` as mutable
    println!("{first}");           // because `first` is still used here
}

push may reallocate, which would leave first dangling. The borrow checker sees that first is still live and refuses.

Two writers are also rejected:

fn main() {
    let mut x = 5;
    let a = &mut x;
    let b = &mut x;                // error[E0499]: second mutable borrow
    *a += 1;
    *b += 1;
}

And you cannot modify through a shared reference:

#![allow(unused)]
fn main() {
fn add(v: &Vec<i32>) {
    v.push(1);                     // error[E0596]: cannot borrow `*v` as mutable
}
}

Borrows end at their last use

A borrow lasts only as long as the reference is used, not until the end of the block (this is called non-lexical lifetimes). This is why the next program is fine:

fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];
    println!("{first}");           // last use of `first`: borrow ends here
    v.push(4);                     // fine now
    println!("{v:?}");
}

Lifetimes

In C

Returning a pointer to a local variable is the textbook dangling pointer. The compiler may warn, but a slightly less obvious version will not be caught.

char *name(void) {
    char buf[16] = "temp";
    return buf;                 /* dangling: buf is gone after return */
}

In Rust

Every reference has a lifetime: the region of code where the value it points to is guaranteed to be alive. Usually the compiler works it out. When it cannot, you add lifetime annotations ('a) so it can check your claim.

Lifetimes are not runtime things. They never allocate or cost anything; they only let the compiler prove that no reference outlives its data.

The dangling pointer from C is rejected:

#![allow(unused)]
fn main() {
fn dangle() -> &String {            // error[E0106]: missing lifetime specifier
    let s = String::from("temp");
    &s                              // s is dropped at the end of the function
}
}

The same mistake through a plain inner block is caught too, because the data does not live long enough:

fn main() {
    let r;
    {
        let x = 5;
        r = &x;                     // error[E0597]: `x` does not live long enough
    }                               // x dies here
    println!("{r}");                // r would dangle
}

The fix is to return the owned value (move it out):

fn make() -> String {
    String::from("temp")
}

fn main() {
    println!("{}", make());
}

Annotations relate lifetimes of inputs and outputs

A function that returns one of its reference arguments must say which. Otherwise the compiler cannot know how long the result is valid.

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let a = String::from("hello");
    let b = String::from("hi");
    println!("{}", longest(&a, &b));
}

Read <'a> as: “there is some lifetime 'a; both inputs live at least that long, and the result is valid for that long”. The result may not be used after either input is gone:

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}

fn main() {
    let a = String::from("hello");
    let result;
    {
        let b = String::from("hi");
        result = longest(&a, &b);   // result may point into b
    }                               // b dropped
    println!("{result}");           // error[E0597]: `b` does not live long enough
}

Elision: most of the time you write nothing

Three rules let the compiler fill in lifetimes in function signatures:

  1. Each reference parameter gets its own lifetime.
  2. If there is exactly one input lifetime, the output uses it.
  3. If one parameter is &self or &mut self, the output uses that lifetime.
fn first_word(s: &str) -> &str {    // really: fn first_word<'a>(s: &'a str) -> &'a str
    s.split_whitespace().next().unwrap_or("")
}

fn main() {
    println!("{}", first_word("hello world"));
}

Structs that hold references

A struct holding a reference needs a lifetime parameter, so it cannot outlive what it points to. In C this is the parser object that quietly keeps a pointer into the input buffer.

struct Parser<'a> {
    input: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn new(input: &'a str) -> Parser<'a> {
        Parser { input, pos: 0 }
    }
    fn rest(&self) -> &'a str {
        &self.input[self.pos..]
    }
}

fn main() {
    let text = String::from("key=value");
    let mut p = Parser::new(&text);
    p.pos = 4;
    println!("{}", p.rest());      // value
}

text must outlive p. If you drop or move text first, it will not compile.

'static

'static means “valid for the whole program”. String literals have it: they live in the read-only data section of the binary.

fn main() {
    let s: &'static str = "baked into the binary";
    println!("{s}");
}

C habits to unlearn

  • Do not return pointers to locals, or keep pointers to buffers that might be freed. Return owned values, or tie the result to an input lifetime.
  • Do not reach for 'static to silence an error. It usually means “leak” or “global”; restructure instead.
  • Do not add lifetimes everywhere. Write the signature without them first and add them only when the compiler asks.

struct Parser<'a> {
    input: &'a str,

    }
}

Stack, heap, Box, Vec, String

In C

Locals live on the stack. Everything of dynamic size comes from malloc, and the size is yours to track. A string is a char * ending in a NUL byte, and its length is found by scanning.

int *v = malloc(n * sizeof *v);       /* you remember n */
v = realloc(v, 2 * n * sizeof *v);    /* may move; old pointers dangle */
char *s = malloc(6); strcpy(s, "hello");
size_t len = strlen(s);               /* O(n) scan for the NUL */
free(v); free(s);

Vec<T>

A Vec<T> stores a pointer, a length and a capacity, the three variables a C program carries around by hand.

fn main() {
    let mut v = Vec::new();
    for i in 0..5 {
        v.push(i * i);                       // grows (reallocates) as needed
    }
    println!("{v:?} len={} cap>={}", v.len(), v.capacity());

    v[1] = 100;                              // indexing is bounds checked
    let total: i32 = v.iter().sum();
    println!("{total}");

    let first = v.first();                   // Option<&i32>
    println!("{first:?}");
    let v2 = vec![1, 2, 3];                  // the vec! macro, like an initializer
    println!("{}", v2.len());
}

A reference into the vector blocks push, so the realloc-invalidates-pointer bug of chapter 8 cannot happen.

String and &str

A String is an owned, growable UTF-8 buffer. A &str is a borrowed view of UTF-8 bytes (pointer + length). There is no NUL terminator; the length is stored, so len() is O(1) and strings may contain zero bytes.

fn greet(name: &str) -> String {        // takes a view, returns an owned string
    let mut out = String::from("hello, ");
    out.push_str(name);
    out.push('!');
    out
}

fn main() {
    let lit = "world";                  // &'static str, in the binary
    let owned = String::from("Rust");   // heap-allocated
    println!("{}", greet(lit));
    println!("{}", greet(&owned));      // &String converts to &str automatically
    println!("{}", lit.len());          // 5, no scan
}

Accept &str in function parameters; it takes both literals and &String.

Strings are UTF-8, so a character may be more than one byte. Indexing a string with an integer is not allowed, because “the nth byte” is rarely what you want:

fn main() {
    let s = String::from("héllo");
    let c = s[1];        // error[E0277]: the type `str` cannot be indexed by `{integer}`
}

Say what you mean instead:

fn main() {
    let s = String::from("héllo");
    println!("{}", s.len());                    // 6 bytes: é takes two
    println!("{}", s.chars().count());          // 5 characters
    println!("{:?}", s.chars().nth(1));         // Some('é')
    println!("{}", &s[0..1]);                   // "h": a byte range
    println!("{}", &s[1..3]);                   // "é"
    for b in s.bytes().take(3) {
        print!("{b} ");                         // 104 195 169
    }
    println!();
    // &s[0..2] would panic: byte 2 is in the middle of é.
}

For raw bytes with no encoding guarantees, use &[u8] / Vec<u8>.

Drop and RAII

In C

Cleanup is written by hand, usually with goto so that every error path releases what has been acquired so far. Forgetting one path leaks.

int process(const char *path) {
    int rc = -1;
    FILE *f = fopen(path, "r");
    if (!f) return -1;
    char *buf = malloc(4096);
    if (!buf) goto close_file;
    if (fread(buf, 1, 4096, f) == 0) goto free_buf;
    rc = 0;
free_buf:
    free(buf);
close_file:
    fclose(f);
    return rc;
}

In Rust

RAII (Resource Acquisition Is Initialization): a value that owns a resource releases it in its destructor, the Drop trait. The compiler calls drop automatically when the owner goes out of scope, on every path: normal exit, early return, ?, or a panic.

struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn main() {
    let _a = Noisy("a");
    let _b = Noisy("b");
    {
        let _c = Noisy("c");
        println!("inner end");
    }                          // c dropped here
    let d = Noisy("d");
    drop(d);                   // explicit early drop (it is just a move)
    println!("main end");
}
// prints: inner end, drop c, drop d, main end, drop b, drop a

Locals are dropped in reverse order of declaration, the same order a careful goto cleanup chain would release them.

Early returns clean up automatically

The goto ladder above disappears:

struct Noisy(&'static str);
impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn work(fail: bool) -> Result<(), String> {
    let _r1 = Noisy("file");
    if fail {
        return Err("failed".to_string());     // _r1 is dropped on this path
    }
    let _r2 = Noisy("buffer");
    Ok(())                                    // both dropped, in reverse
}

fn main() {
    println!("{:?}", work(true));
    println!("{:?}", work(false));
}

Standard types already do this

File closes the descriptor, Vec and String free their buffers, Box frees its allocation, and MutexGuard unlocks the mutex, all through Drop.

use std::fs::File;
use std::io::Read;

fn read_head(path: &str) -> std::io::Result<String> {
    let mut f = File::open(path)?;          // no fclose anywhere
    let mut s = String::new();
    f.read_to_string(&mut s)?;
    Ok(s)
}   // f closed here, even if `?` returned early

fn main() {
    println!("{}", read_head("/definitely/not/here").is_err());   // true
}

Drop and moves

A moved value is dropped by its new owner, once. The old name is not dropped (it no longer owns anything).

struct Noisy(&'static str);
impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

fn take(n: Noisy) {
    println!("took {}", n.0);
}   // dropped here, not in main

fn main() {
    let a = Noisy("a");
    take(a);
    println!("back in main");
}

Rules and escape hatches

  • You cannot call x.drop() yourself; use drop(x) (moves it into a function that does nothing) to release early.
  • A type with a Drop implementation cannot also be Copy.
  • Fields drop in declaration order, after the struct’s own drop runs.
  • std::mem::forget(x) skips the destructor. Leaking is safe in Rust (it is not undefined behavior), just wasteful; the language prevents memory unsafety, not all leaks. Reference cycles with Rc can leak.
  • During a panic, destructors run while unwinding. With panic = "abort" they do not.

Raw pointers and unsafe

In C

Every pointer is raw. You may add, subtract, cast, compare, and dereference any pointer anywhere, and the compiler trusts you completely.

int a[3] = {1, 2, 3};
int *p = a;
int x = *(p + 2);          /* pointer arithmetic */
*(char *)p = 0;            /* reinterpret memory */

In Rust

Rust has the same raw pointers, *const T and *mut T, but they live behind a marker. Code that can break memory safety must be in an unsafe block or unsafe fn. The vast majority of Rust code never needs it.

fn main() {
    let mut x = 10;
    let p = &mut x as *mut i32;   // creating a raw pointer is safe
    unsafe {
        *p += 5;                  // dereferencing is the unsafe part
    }
    println!("{x}");              // 15
}

What unsafe allows (and only this)

Inside an unsafe block you gain five extra abilities:

  1. dereference a raw pointer,
  2. call an unsafe function (including C functions through FFI),
  3. access or modify a static mut,
  4. implement an unsafe trait (such as Send),
  5. read a field of a union.

What unsafe does not do

It does not turn off the type checker or the borrow checker. Ordinary references inside an unsafe block are still checked. It only means: “for these operations, the compiler cannot verify safety, so I take responsibility.”

You are still bound by the rules; breaking them is undefined behavior, as in C: no dangling or null dereference, no data races, no aliasing a &mut, no invalid values (a bool that is not 0 or 1), and so on.

Pointer arithmetic

fn main() {
    let a = [1, 2, 3];
    let p = a.as_ptr();                    // *const i32 to the first element
    unsafe {
        for i in 0..a.len() {
            print!("{} ", *p.add(i));      // like *(p + i); counts in elements
        }
    }
    println!();

    let null: *const i32 = std::ptr::null();
    println!("{}", null.is_null());        // true; *null would be UB
}

Building a safe API on unsafe

The idiom is to keep unsafe small, check its preconditions, and expose a safe function. The standard library does this everywhere. Here is split_at_mut: two non-overlapping &mut slices of one array, which the borrow checker cannot verify by itself.

use std::slice;

fn split_at_mut(xs: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = xs.len();
    let p = xs.as_mut_ptr();
    assert!(mid <= len);                        // the safety condition, checked
    unsafe {
        (
            slice::from_raw_parts_mut(p, mid),
            slice::from_raw_parts_mut(p.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut a = [1, 2, 3, 4, 5];
    let (left, right) = split_at_mut(&mut a, 2);
    left[0] = 10;
    right[0] = 30;
    println!("{a:?}");                          // [10, 2, 30, 4, 5]
}

Callers of split_at_mut need no unsafe and cannot misuse it.

unsafe fn and documenting the contract

/// # Safety
/// `p` must be non-null, aligned, and point to a valid, initialized `i32`.
unsafe fn read(p: *const i32) -> i32 {
    unsafe { *p }
}

fn main() {
    let x = 7;
    let v = unsafe { read(&x) };               // caller promises the contract
    println!("{v}");
}

This is the Rust analogue of handing ownership across an API boundary:

Under the hood

  • A raw pointer has the same representation as a C pointer: one machine word (two for a pointer to a slice or trait object). A dereference compiles to a plain load or store.
  • unsafe has no runtime cost and no effect on code generation. It is a compile-time marker for humans and tools.
  • Undefined behavior in unsafe can break the guarantees of the safe code around it. That is why unsafe blocks should be tiny and wrapped in safe APIs.

  • Do not leave unsafe code undocumented. State the contract (# Safety) and check it in the safe wrapper.
  • Do not assume anything works “because it does in C”: Rust’s aliasing rules for &/&mut are stricter, even inside unsafe.

Methods and associated functions

In C

There are no methods. The convention is a struct plus functions that take a pointer to it as the first argument, named with a prefix, and an init function that fills in a caller-provided struct.

struct stack { int *items; size_t len, cap; };

void stack_init(struct stack *s);
int  stack_push(struct stack *s, int x);
size_t stack_len(const struct stack *s);   /* const: read-only */
void stack_free(struct stack *s);

In Rust

An impl block attaches functions to a type. A function whose first parameter is self is a method, called with dot syntax. The kind of self says how it uses the value, which is exactly the const T * / T * / by-value distinction in C, checked by the compiler.

#[derive(Debug, Default)]
struct Stack {
    items: Vec<i32>,
}

impl Stack {
    const MAX: usize = 4;                       // associated constant

    fn new() -> Self {                          // associated function (a constructor)
        Self::default()
    }

    fn push(&mut self, x: i32) -> Result<(), i32> {
        if self.items.len() == Self::MAX {
            return Err(x);                      // full: hand the value back
        }
        self.items.push(x);
        Ok(())
    }

    fn pop(&mut self) -> Option<i32> {
        self.items.pop()
    }

    fn len(&self) -> usize {
        self.items.len()
    }

    fn into_vec(self) -> Vec<i32> {             // consumes the stack
        self.items
    }
}

fn main() {
    let mut s = Stack::new();                   // no stack_init, no out-pointer
    for i in 0..6 {
        if let Err(x) = s.push(i) {
            println!("full, rejected {x}");
        }
    }
    println!("{} {:?}", s.len(), s.pop());      // 4 Some(3)
    let v = s.into_vec();                       // s is moved
    println!("{v:?}");
}

Self means “the type this impl is for”. Stack::new() is not special; it is a plain function in the type’s namespace. There is no stack_free: the Vec inside is dropped with the struct (chapter 11).

The method call is sugar

s.len() is exactly Stack::len(&s). The compiler inserts the & or &mut (auto-reference), so you never write (&s)-> or (*p).:

struct Counter { n: u32 }
impl Counter {
    fn bump(&mut self) { self.n += 1; }
}

fn main() {
    let mut c = Counter { n: 0 };
    c.bump();                 // same as Counter::bump(&mut c)
    Counter::bump(&mut c);
    println!("{}", c.n);      // 2
}

A consuming method ends the value’s life:

struct Stack { items: Vec<i32> }
impl Stack {
    fn into_vec(self) -> Vec<i32> { self.items }
}

fn main() {
    let s = Stack { items: vec![1] };
    let v = s.into_vec();
    println!("{}", s.items.len());   // error[E0382]: borrow of moved value: `s`
    println!("{v:?}");
}

Several impl blocks and derive

A type may have any number of impl blocks. #[derive(...)] generates common implementations for you: Debug (printing with {:?}), Clone, Copy, PartialEq, Default, and others.

#[derive(Debug, Clone, Copy, PartialEq)]
struct Point {
    x: i32,
    y: i32,
}

impl Point {
    fn manhattan(&self) -> i32 {
        self.x.abs() + self.y.abs()
    }
}

fn main() {
    let a = Point { x: 3, y: -4 };
    let b = a;                         // Copy: `a` stays valid
    println!("{:?} {} {}", b, a == b, a.manhattan());
}

There is no inheritance. Types share behavior through traits (chapter 15), which cover the job of a C “ops table”.

  • Choose the weakest self: &self by default, &mut self to modify, self only when consuming.

Option, Result and ?

In C

Absence and failure are signaled by in-band values that the compiler cannot make you check: NULL, -1, errno, or a boolean plus an out-parameter.

char *p = getenv("HOME");       /* NULL if absent */
printf("%s\n", p);              /* NULL dereference if you forgot */

int n = atoi("abc");            /* 0 on error: indistinguishable from "0" */

int fd = open(path, O_RDONLY);
if (fd < 0) { perror("open"); return -1; }   /* errno is global state */

In Rust

Both are ordinary enums, and you must handle them to get the value out.

enum Option<T> { Some(T), None }          // a value, or nothing
enum Result<T, E> { Ok(T), Err(E) }       // a value, or an error

Option<T>: the safe NULL

fn find(xs: &[i32], target: i32) -> Option<usize> {
    for (i, &x) in xs.iter().enumerate() {
        if x == target {
            return Some(i);
        }
    }
    None
}

fn main() {
    let xs = [10, 20, 30];
    match find(&xs, 20) {
        Some(i) => println!("found at {i}"),
        None => println!("not found"),
    }
    if let Some(i) = find(&xs, 99) {
        println!("{i}");
    } else {
        println!("missing");
    }
}

You cannot use an Option<i32> as an i32; the types differ, so forgetting the None case does not compile:

fn main() {
    let x: Option<i32> = Some(1);
    let y = x + 1;          // error[E0369]: cannot add `{integer}` to `Option<i32>`
    println!("{y}");
}

Handy methods avoid a match each time:

fn main() {
    let a: Option<i32> = Some(4);
    let b: Option<i32> = None;

    println!("{}", a.unwrap_or(0));                 // 4
    println!("{}", b.unwrap_or(0));                 // 0
    println!("{:?}", a.map(|x| x * 2));             // Some(8)
    println!("{:?}", a.and_then(|x| x.checked_sub(10))); // Some(-6)
    println!("{}", a.is_some());                    // true
    println!("{}", a.expect("a was None"));         // 4; panics with this message if None
}

unwrap() and expect() panic on None. They are fine in tests and examples; in real code prefer match, ?, or a default.

Result<T, E>: errors as values

fn parse_sum(a: &str, b: &str) -> Result<i32, std::num::ParseIntError> {
    let x: i32 = a.parse()?;    // `?` returns early with the error
    let y: i32 = b.parse()?;
    Ok(x + y)
}

fn main() {
    println!("{:?}", parse_sum("2", "3"));      // Ok(5)
    println!("{:?}", parse_sum("2", "x"));      // Err(ParseIntError { kind: InvalidDigit })
}

The ? operator means: “if this is Ok(v), give me v; if it is Err(e), return Err(e) from the current function.” It replaces the if (rc < 0) return rc; after every call. Both Result and Option work with ?.

A function that uses ? must itself return a compatible Result/Option.

Your own error type, and From

? also converts the error with the From trait, so one function can mix error sources:

use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    Missing(String),
    BadNumber(ParseIntError),
}

impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self {
        ConfigError::BadNumber(e)
    }
}

fn port(value: Option<&str>) -> Result<u16, ConfigError> {
    let s = value.ok_or_else(|| ConfigError::Missing("port".to_string()))?;
    Ok(s.parse::<u16>()?)       // ParseIntError converted by From
}

fn main() {
    println!("{:?}", port(Some("8080")));
    println!("{:?}", port(None));
    println!("{:?}", port(Some("http")));
}

An enum error lists every way the function can fail, which errno never did.

main can return a Result

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let n: i32 = "42".parse()?;
    println!("{n}");
    Ok(())              // a returned Err prints the error and exits with code 1

Under the hood

  • Option<T> costs nothing extra when T has an invalid bit pattern to spare. Option<&T> and Option<Box<T>> are the same size as the pointer, with None stored as null. Rust’s Option<&T> is C’s nullable pointer, with the null check forced on you.

  • Result is likewise an ordinary enum: no exceptions, no unwinding tables for errors, no global state. The ? is a branch on the tag and an early return.

C habits to unlearn

  • Do not return sentinel values. Return Option or Result.
  • Do not use a global like errno. The error travels with the return value.
  • Do not unwrap() to silence the compiler in production code. Decide what the failure means.
  • Do not ignore a Result: the compiler warns about unused results (#[must_use]).

Traits and generics

In C

To write one function for many types, C offers void * plus a size and a function pointer, or preprocessor macros.

/* type-erased: no type checking, a call through a pointer per comparison */
void qsort(void *base, size_t n, size_t size,
           int (*cmp)(const void *, const void *));

/* macro: duplicated per use, no type check, double evaluation */
#define MAX(a, b) ((a) > (b) ? (a) : (b))
int m = MAX(i++, j);       /* i++ may run twice */

In Rust

Generics write code once for many types, and the compiler checks it. Traits describe what a type can do, and generic code states which capabilities it needs (a bound).

A trait is a set of required functions

trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> String {          // a default method, which types may override
        String::from("shape")
    }
}

struct Circle(f64);
struct Square(f64);

impl Shape for Circle {
    fn area(&self) -> f64 { 3.14159 * self.0 * self.0 }
    fn name(&self) -> String { String::from("circle") }
}

impl Shape for Square {
    fn area(&self) -> f64 { self.0 * self.0 }
}

fn print_area<T: Shape>(s: &T) {        // T must implement Shape
    println!("{} {}", s.name(), s.area());
}

fn main() {
    print_area(&Circle(1.0));
    print_area(&Square(2.0));
}

Generic functions with bounds

fn largest<T: PartialOrd + Copy>(xs: &[T]) -> T {
    let mut m = xs[0];
    for &x in xs {
        if x > m {
            m = x;
        }
    }
    m
}

fn main() {
    println!("{}", largest(&[3, 9, 2]));          // i32
    println!("{}", largest(&[1.5, 0.2]));         // f64
    println!("{}", largest(&['a', 'z', 'q']));    // char
}

T: PartialOrd + Copy reads “T can be compared with </> and copied”. Without the bound the body is rejected; the compiler will not let you call > on a type that may not have it:

#![allow(unused)]
fn main() {
fn largest<T>(a: T, b: T) -> T {
    if a > b { a } else { b }    // error[E0369]: binary operation `>` cannot be applied to type `T`
}
}

Under the hood

  • Generics are monomorphized: for each concrete type used, the compiler generates a specialized copy of the function (largest::<i32>, largest::<f64>), as if you had written each by hand. There is no void *, no indirect call and no runtime type information, and every copy is fully optimized and inlinable.
  • The cost is code size and compile time, the same trade-off as C++ templates or macro-generated code, but type-checked once against the trait bound.
  • Trait methods on a concrete type are direct calls. For a call through a pointer, see dyn Trait in the next chapter.
  • Traits are open: you can implement your trait for someone else’s type, or someone else’s trait for your type, but not both foreign (the orphan rule).

C habits to unlearn

  • Do not erase types with void * to share code. Use generics.
  • Do not write macros to generate per-type functions. A generic function is checked, not text-pasted.
  • Do not add bounds you do not use; add exactly the ones the compiler asks for.

dyn Trait and impl Trait

In C

When the concrete type is only known at run time, C uses a vtable: a struct of function pointers, plus a void * to the object.

struct shape_vtable {
    double (*area)(const void *self);
};

struct shape {
    const struct shape_vtable *vt;
    const void *self;
};

struct circle { double r; };

static double circle_area(const void *self) {
    const struct circle *c = self;          /* the cast is on you */
    return 3.14159 * c->r * c->r;
}
static const struct shape_vtable circle_vt = { circle_area };

/* struct shape s = { &circle_vt, &my_circle };  call: s.vt->area(s.self) */

You maintain the table, the casts, and the pairing of table with object by hand.

In Rust

A trait object, written dyn Trait, is exactly that pair, built and checked by the compiler. It is used behind a pointer: &dyn Trait, Box<dyn Trait>.

trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> &str;
}

struct Circle(f64);
struct Rect(f64, f64);

impl Shape for Circle {
    fn area(&self) -> f64 { 3.14159 * self.0 * self.0 }
    fn name(&self) -> &str { "circle" }
}
impl Shape for Rect {
    fn area(&self) -> f64 { self.0 * self.1 }
    fn name(&self) -> &str { "rect" }
}

fn main() {
    // one collection, different concrete types
    let shapes: Vec<Box<dyn Shape>> = vec![Box::new(Circle(1.0)), Box::new(Rect(2.0, 3.0))];
    for s in &shapes {
        println!("{} {}", s.name(), s.area());     // dynamic dispatch
    }
    let total: f64 = shapes.iter().map(|s| s.area()).sum();
    println!("{total}");
}

dyn Shape itself has no known size, so it cannot be a local or a Vec element directly; it must sit behind a pointer:

trait Shape { fn area(&self) -> f64; }
struct Circle(f64);
impl Shape for Circle { fn area(&self) -> f64 { self.0 } }

fn main() {
    let s: dyn Shape = Circle(1.0);   // error[E0277]: the size for values of type `dyn Shape` cannot be known
                                      // (rustc also reports E0308 mismatched types here)
}

impl Trait in arguments and return types

impl Trait is short for “some specific type implementing this trait”. In an argument it is a generic with the name left out:

trait Shape { fn area(&self) -> f64; }
struct Square(f64);
impl Shape for Square { fn area(&self) -> f64 { self.0 * self.0 } }

fn describe(s: &impl Shape) -> String {       // same as fn describe<T: Shape>(s: &T)
    format!("area = {}", s.area())
}

fn main() {
    println!("{}", describe(&Square(3.0)));
}

In a return position it hides a type that you cannot or do not want to name, such as a closure or an iterator chain. It is still one concrete type, resolved at compile time:

fn evens(limit: u32) -> impl Iterator<Item = u32> {
    (0..limit).filter(|x| x % 2 == 0)
}

fn main() {
    let v: Vec<u32> = evens(10).collect();
    println!("{v:?}");                         // [0, 2, 4, 6, 8]
}

To return one of several different types at run time, return Box<dyn Trait>.

Dyn compatibility (object safety)

Only some traits can become dyn; the Reference calls them dyn compatible (older texts say object safe). A method must not be generic and must not return Self by value, because the compiler cannot build a single vtable entry for it. A method can opt out with where Self: Sized, which keeps it callable on concrete types and leaves it out of the vtable. Traits that are not dyn compatible can still be used as generic bounds.

  • Besides method pointers, the vtable holds the size, alignment and a destructor, so a Box<dyn Shape> can be freed correctly.
  • A dyn call is an indirect call; the optimizer usually cannot inline it, which is the same cost as the C vtable.

C habits to unlearn

  • Do not hand-roll vtables and casts. Declare a trait and a dyn.
  • Do not use dyn only to avoid writing generics; you give up inlining.
  • Do not return a closure by function pointer. Use impl Fn or Box<dyn Fn>.

Closures

In C

A callback is a function pointer. To give the function some state, you pass an extra void *ctx and cast it back inside. You must also keep that context alive yourself.

struct ctx { int offset; };

static int add_offset(int x, void *p) {
    struct ctx *c = p;
    return x + c->offset;
}

void apply_all(int *a, size_t n, int (*f)(int, void *), void *ctx);
/* apply_all(a, n, add_offset, &(struct ctx){ 10 }); */

In Rust

A closure is an anonymous function that can capture variables from where it is written. It is written |params| body.

fn apply<F: Fn(i32) -> i32>(f: F, x: i32) -> i32 {
    f(x)
}

fn main() {
    let offset = 10;
    let add = |x| x + offset;        // captures `offset`
    println!("{}", apply(add, 5));   // 15
    println!("{}", apply(|x| x * 2, 5));   // 10
}

The compiler turns the closure into an unnamed struct holding the captured variables, plus a call function: the ctx and the callback bundled together automatically, with correct types and no casts.

Three kinds: Fn, FnMut, FnOnce

    call_twice(|| count += 1);        // mutates the captured `count`

A closure that moves a value out can only be called once, and the compiler enforces it:

fn main() {
    let s = String::from("data");
    let f = move || s;                // returns (moves out) s: FnOnce
    let a = f();
    let b = f();                      // error[E0382]: use of moved value: `f`
    println!("{a} {b}");
}

Capturing by reference or by move

By default a closure borrows what it uses, so the usual borrowing rules apply. move makes it take ownership of the captures, which is needed when the closure outlives the current function (returning it, or sending it to a thread).

fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    move |x| x + n                    // n is copied into the closure
}

fn main() {
    let add5 = make_adder(5);
    println!("{}", add5(10));         // 15
}

Without move the closure would borrow n, a local that dies when make_adder returns: the dangling-pointer bug, rejected at compile time.

#![allow(unused)]
fn main() {
fn make_adder(n: i32) -> impl Fn(i32) -> i32 {
    |x| x + n          // error[E0373]: closure may outlive the current function
}
}

Storing different closures

Each closure has its own unnamed type, so a collection of different closures uses Box<dyn Fn...> (chapter 16):

fn main() {
    let ops: Vec<Box<dyn Fn(i32, i32) -> i32>> = vec![
        Box::new(|a, b| a + b),
        Box::new(|a, b| a * b),
    ];
    for f in &ops {
        println!("{}", f(3, 4));          // 7, then 12
    }
}

Most callbacks in Rust are closures passed to iterator methods (next chapter):

Under the hood

  • A closure is a struct of its captures. A non-capturing closure is zero-sized. size_of_val(&add) equals the size of what it captured (a borrowed variable is captured as a pointer).
  • A generic F: Fn(...) is monomorphized: the call is a direct call and is usually inlined, so a closure passed to map costs no more than a hand-written loop body.
  • A Box<dyn Fn> adds a heap allocation and an indirect call, like a function pointer plus a malloc’d context.

  • Do not define a context struct and a void * cast for each callback.
  • Do not worry about who frees the context; the closure owns its captures.
  • Prefer generic F: Fn parameters over Box<dyn Fn> unless you must store different closures together.

Iterators and collections

In C

You loop with an index or a pointer, and you write (or find) your own growable array and hash table. Loop bounds are your responsibility.

int total = 0;
for (size_t i = 0; i < n; i++) {
    if (a[i] % 2 == 0) total += a[i] * a[i];
}

In Rust

An iterator produces items one at a time. Its whole interface is one method, next(), which returns Some(item) or None when finished. for loops and a large toolbox of adapters are built on it.

fn main() {
    let v = vec![1, 2, 3, 4, 5, 6];

    let total: i32 = v
        .iter()
        .filter(|&&x| x % 2 == 0)     // keep evens
        .map(|&x| x * x)              // square them
        .sum();                       // consume: 4 + 16 + 36
    println!("{total}");              // 56
}

That is the C loop above, with no index to get wrong and no mutable accumulator.

Common adapters and consumers

fn main() {
    let v = vec![3, 1, 4, 1, 5, 9, 2, 6];

    let squares: Vec<i32> = v.iter().map(|x| x * x).collect();     // build a Vec
    println!("{squares:?}");

    println!("{}", v.iter().count());                      // 8
    println!("{:?}", v.iter().max());                      // Some(9)
    println!("{}", v.iter().any(|&x| x == 4));             // true
    println!("{}", v.iter().all(|&x| x > 0));              // true
    println!("{:?}", v.iter().position(|&x| x == 5));      // Some(4)
    println!("{}", v.iter().fold(0, |acc, x| acc + x));    // 31

    for (a, b) in v.iter().zip(v.iter().skip(1)).take(3) { // pairs of neighbors
        print!("({a},{b}) ");
    }
    println!();

    let words = ["a", "b", "c"];
    for (i, w) in words.iter().enumerate() {               // index + item
        print!("{i}:{w} ");
    }
    println!();
}

Adapters (map, filter, zip, take, skip, rev, enumerate, chain) are lazy: they do nothing until a consumer (sum, collect, count, a for loop) pulls items.

Writing your own iterator

struct Countdown(u32);

impl Iterator for Countdown {
    type Item = u32;

    fn next(&mut self) -> Option<u32> {
        if self.0 == 0 {
            None
        } else {
            self.0 -= 1;
            Some(self.0 + 1)
        }
    }
}

fn main() {
    let v: Vec<u32> = Countdown(3).collect();
    println!("{v:?}");                  // [3, 2, 1]
    println!("{}", Countdown(4).sum::<u32>());   // 10; every adapter now works for free
}

use std::collections::HashMap;

fn main() {
    let text = "a b a c b a";
    let mut counts: HashMap<&str, i32> = HashMap::new();
    for w in text.split_whitespace() {
        *counts.entry(w).or_insert(0) += 1;     // insert 0 if absent, then add 1
    }

    println!("{:?}", counts.get("a"));          // Some(3)
    println!("{:?}", counts.get("z"));          // None

    let mut pairs: Vec<_> = counts.iter().collect();
    pairs.sort();                               // HashMap order is unspecified
    println!("{pairs:?}");                      // [("a", 3), ("b", 2), ("c", 1)]
}

HashMap iteration order is randomized per run (to resist hash flooding). Sort the keys, or use BTreeMap, when you need a stable order. get returns Option, so a missing key cannot be mistaken for a value.

Under the hood

  • Iterator chains are zero cost: after inlining they typically compile to the same loop as the hand-written C, often with bounds checks removed and vectorization enabled. Compare them on Compiler Explorer.
  • Vec iteration over a slice is a pointer walking from start to end, like for (p = a; p != a + n; p++).

  • Laziness means no intermediate arrays are allocated between adapters.

  • Do not index to loop; iterate. Use an index only when the index itself matters, and then prefer enumerate().
  • Do not allocate temporary arrays between stages; chain the adapters.
  • Do not write your own hash table or dynamic array.
  • Do not depend on HashMap order.

Modules and visibility

In C

Code is split into .c files, and the interface is in .h files that others #include. Everything is visible across files unless marked static. Include guards prevent double inclusion, and the linker resolves names.

/* stack.h */
#ifndef STACK_H
#define STACK_H
struct stack;                       /* opaque type */
struct stack *stack_new(void);
#endif

/* stack.c */
#include "stack.h"
static void helper(void) {}         /* file-private */

In Rust

A crate is a tree of modules. A module groups items and controls visibility. Everything is private by default; you opt in with pub. There are no header files, no include guards, and no separate declarations.

mod geometry {
    pub struct Point {
        pub x: i32,
        pub y: i32,
    }

    pub fn origin() -> Point {
        Point { x: 0, y: 0 }
    }

    fn helper() {}                      // private: like a `static` function

    pub mod shapes {
        use super::Point;               // `super` = the enclosing module

        pub fn dist2(a: &Point, b: &Point) -> i32 {
            (a.x - b.x).pow(2) + (a.y - b.y).pow(2)
        }
    }
}

use geometry::shapes::dist2;
use geometry::{origin, Point};

fn main() {
    let p = Point { x: 3, y: 4 };
    println!("{}", dist2(&p, &origin()));   // 25
}

Using a private item from outside is an error:

mod m {
    fn secret() {}
}

fn main() {
    m::secret();       // error[E0603]: function `secret` is private
}

Splitting across files

A module declaration with a semicolon tells the compiler to load the module from another file. The file layout mirrors the module tree:

src/
  main.rs            // crate root:   mod stack;  mod net;
  stack.rs           // module `stack`
  net/
    mod.rs           // module `net` (or net.rs next to the net/ folder)
    tcp.rs           // module `net::tcp`, declared with `mod tcp;` inside net

// main.rs
mod stack;                    // loads stack.rs
use stack::Stack;

fn main() {
    let mut s = Stack::new();
    s.push(1);
}

// stack.rs
pub struct Stack { items: Vec<i32> }      // field stays private
impl Stack {
    pub fn new() -> Stack { Stack { items: Vec::new() } }
    pub fn push(&mut self, x: i32) { self.items.push(x); }
}

Because items is private, code outside the module cannot touch it: a struct with private fields is an opaque type, the role struct stack; plus accessor functions plays in C, without a header.

Under the hood

  • Modules exist only at compile time. All items of a crate compile together, so the order of mod declarations and definitions is irrelevant, and calls across modules are inlined like any other.
  • Because the whole crate is one compilation unit, there are no duplicate-symbol or header-order problems.
  • Visibility is purely a compile-time check. It has no effect on the generated code, but it is what lets you keep invariants: if a field is private, only code in the module can break it.

  • Do not use name prefixes; use modules.
  • Do not expose struct fields that carry invariants; give methods instead.

Macros

In C

The preprocessor rewrites text before the compiler sees it. It has no idea about types, scopes or expression boundaries, which produces classic bugs.

#define SQUARE(x) x * x
int a = SQUARE(1 + 2);          /* 1 + 2 * 1 + 2 == 5, not 9 */

#define SWAP(a, b) { int tmp = a; a = b; b = tmp; }
int tmp = 1, y = 2;
SWAP(tmp, y);                   /* expands to int tmp = tmp; ... : wrong */

#define MAX(a, b) ((a) > (b) ? (a) : (b))
int m = MAX(i++, j);            /* i++ may be evaluated twice */

In Rust

A Rust macro works on the syntax tree, not on text. Macros are invoked with a !, like println!, vec!, assert_eq!. You will use the standard ones every day and write your own rarely.

fn main() {
    let v = vec![1, 2, 3];                       // builds a Vec
    assert_eq!(v.len(), 3);                      // checks, prints both sides on failure
    println!("{} {:?}", v.len(), v);             // formatting checked at compile time
}

println!("{}") with a missing argument is a compile error, where printf is silent undefined behavior:

fn main() {
    println!("{} {}", 1);     // error: 2 positional arguments in format string, but there is 1 argument
}

Declarative macros: macro_rules!

A macro is a set of patterns that match the tokens at the call site and produce code. Fragment types such as expr, ident and ty say what each part must be.

macro_rules! square {
    ($x:expr) => {{
        let v = $x;                  // evaluate the argument once
        v * v
    }};
}

fn main() {
    println!("{}", square!(1 + 2));  // 9: the argument is one expression, not loose text
}

Unlike C, $x is a whole expression node, so 1 + 2 is not re-associated. Hygiene also keeps the macro’s own v from clashing with the caller’s variables, which solves the SWAP(tmp, y) bug:

macro_rules! swap {
    ($a:ident, $b:ident) => {
        let tmp = $a;                // this `tmp` is invisible to the caller
        $a = $b;
        $b = tmp;
    };
}

fn main() {
    let mut tmp = 1;
    let mut y = 2;
    swap!(tmp, y);                   // works even though the caller also has `tmp`
    println!("{tmp} {y}");           // 2 1
}

Macros can take a variable number of arguments with repetition $( ... ),* and can call themselves:

macro_rules! max {
    ($x:expr) => ($x);
    ($x:expr, $($rest:expr),+) => {{
        let a = $x;
        let b = max!($($rest),+);
        if a > b { a } else { b }
    }};
}

fn main() {
    println!("{}", max!(3, 9, 4));   // 9
}

Note that the macro pastes the argument’s code in for every $x it mentions, which is why square first binds let v = $x;.

Other kinds of macros

  • Derive macros (#[derive(Debug, Clone)]) generate trait implementations.
  • Attribute macros (#[test], #[tokio::main]) transform an item.
  • Procedural macros are Rust programs that run at compile time on the token stream. They are written in their own crate. They replace code generators and X-macros.

FFI: calling C from Rust and Rust from C

In C

Linking two C translation units needs only matching declarations. Types, layout and calling convention are the platform’s, and the linker joins symbols by name.

/* util.h */
int util_add(int a, int b);
/* main.c */
#include "util.h"
int main(void) { return util_add(1, 2); }

In Rust

Rust has its own unstable ABI and layout, so crossing into C requires saying so explicitly: extern "C" for the calling convention, #[repr(C)] for the layout, and unsafe because the compiler cannot check what is on the other side.

Calling C from Rust

Declare the foreign functions in an unsafe extern "C" block. The C library is already linked into every Rust program on most platforms, so this runs as is:

use std::ffi::{c_char, c_int, CString};

unsafe extern "C" {
    fn abs(x: c_int) -> c_int;
    fn strlen(s: *const c_char) -> usize;
}

fn main() {
    let s = CString::new("hello").unwrap();   // NUL-terminated copy
    unsafe {
        println!("{}", abs(-5));              // 5
        println!("{}", strlen(s.as_ptr()));   // 5
    }
}

Every call is unsafe: the compiler trusts your declaration. A wrong signature is undefined behavior, as in C with a mismatched prototype. To link your own C library, add #[link(name = "foo")] on the block or a build.rs that compiles it (the cc crate does this).

Strings across the boundary

Rust strings are not NUL-terminated and may contain zero bytes; C strings are the opposite. Use CString (owned, adds the NUL) to hand text to C and CStr (borrowed) to read text from C:

use std::ffi::{c_char, CStr, CString};

fn main() {
    let owned = CString::new("hi").unwrap();
    let p: *const c_char = owned.as_ptr();           // valid while `owned` lives
    let back: &CStr = unsafe { CStr::from_ptr(p) };  // a view of the C string
    println!("{}", back.to_str().unwrap());          // hi
    // CString::new("a\0b") would return Err: interior NUL
}

Do not keep as_ptr() of a temporary: CString::new("x").unwrap().as_ptr() dangles at the end of the statement.

Layout: #[repr(C)]

use std::mem::{align_of, size_of};

struct Header {      // identical layout to: struct header { uint8_t kind; uint32_t len; uint8_t flag; };
    kind: u8,
    len: u32,
    flag: u8,
}

fn main() {
    println!("{} {}", size_of::<Header>(), align_of::<Header>());  // 12 4
}

Without repr(C) Rust may reorder fields. Other layout attributes: #[repr(u8)] (enum with a fixed integer size), #[repr(transparent)] (a wrapper with exactly the layout of its one field), #[repr(packed)] (no padding, and taking references to its fields is a hazard).

Callbacks: passing Rust functions to C

An extern "C" fn is a plain C function pointer. This calls the C library’s qsort:

use std::ffi::c_void;

unsafe extern "C" {
    fn qsort(
        base: *mut c_void,
        n: usize,
        size: usize,
        cmp: extern "C" fn(*const c_void, *const c_void) -> i32,
    );
}

extern "C" fn cmp_i32(a: *const c_void, b: *const c_void) -> i32 {
    let (a, b) = unsafe { (*(a as *const i32), *(b as *const i32)) };
    a.cmp(&b) as i32                       // Ordering is -1, 0, 1
}

fn main() {
    let mut v = [5, 2, 9, 1];
    unsafe {
        qsort(v.as_mut_ptr() as *mut c_void, v.len(), size_of::<i32>(), cmp_i32);
    }
    println!("{v:?}");                     // [1, 2, 5, 9]
}

A closure cannot be passed directly: C has nowhere to put its captured state. Use the usual C pattern, a void *ctx parameter pointing at your data.

Calling Rust from C

Export a function with an unmangled name and the C ABI, and build the crate as a static or dynamic library:

// src/lib.rs
#[unsafe(no_mangle)]
pub extern "C" fn rs_add(a: i32, b: i32) -> i32 {
    a + b
}
# Cargo.toml

The tool cbindgen generates the C header from your Rust, and bindgen generates Rust declarations from a C header, so neither side is written twice.

A panic must not unwind into C. An extern "C" function aborts the process if a panic escapes it. Catch errors and return a status code (or use catch_unwind).

Ownership across the boundary

Hand a heap value to C as a raw pointer and take it back later with the matching function. Never free Rust memory with free, or C memory with Rust’s drop; each side must release with its own allocator:

pub struct Counter { n: u32 }

#[unsafe(no_mangle)]
pub extern "C" fn counter_new() -> *mut Counter {
    Box::into_raw(Box::new(Counter { n: 0 }))     // ownership leaves Rust
}

#[unsafe(no_mangle)]
pub extern "C" fn counter_bump(c: *mut Counter) -> u32 {
    let c = unsafe { c.as_mut() }.expect("null counter");
    c.n += 1;
    c.n
}

#[unsafe(no_mangle)]
pub extern "C" fn counter_free(c: *mut Counter) {
    if !c.is_null() {
        drop(unsafe { Box::from_raw(c) });           // ownership returns, then freed
    }
}

This is the opaque-handle pattern from C, with the allocation and the free defined together.

Under the hood

Concurrency

In C

Threads share all memory by default. Data races are undefined behavior, and the compiler does not know which variables a mutex protects. The mutex and the data it guards are separate objects, tied together only by discipline.

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
long counter;                       /* nothing says `lock` protects this */

void *worker(void *arg) {
    for (int i = 0; i < 1000; i++) {
        pthread_mutex_lock(&lock);
        counter++;                  /* forget the lock: data race, UB */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}

In Rust

The ownership rules that prevent dangling pointers also prevent data races: the compiler rejects code that shares mutable data between threads without synchronization.

Threads

use std::thread;

fn main() {
    let name = String::from("worker");
    let handle = thread::spawn(move || {          // move: the thread owns `name`
        println!("hello from {name}");
        42
    });
    let result = handle.join().unwrap();          // wait; get the return value
    println!("{result}");
}

spawn requires the closure to own everything it uses, because the thread may outlive the function. Borrowing a local is rejected:

use std::thread;

fn main() {
    let mut count = 0;
    let h = thread::spawn(|| count += 1);   // error[E0373]: closure may outlive the current function
    h.join().unwrap();
}

Mutex: the lock owns the data

use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));         // data lives inside the Mutex
    let mut handles = Vec::new();

    for _ in 0..4 {
        let c = Arc::clone(&counter);              // another owner (reference-counted)
        handles.push(thread::spawn(move || {
            for _ in 0..1000 {
                *c.lock().unwrap() += 1;           // lock, modify, unlock when the guard drops
            }
        }));
    }
    for h in handles {
        h.join().unwrap();
    }
    println!("{}", *counter.lock().unwrap());      // 4000
}
  • Mutex<T> contains the T. The only way to reach it is lock(), which returns a guard; the lock is released when the guard is dropped (chapter 11). You cannot forget to unlock, and cannot touch the data without locking.
  • Arc<T> is an atomically reference-counted shared pointer, the safe version of “several threads hold a pointer, the last one frees it”.

Send and Sync: the compiler’s data-race check

Two marker traits, derived automatically:

  • T: Send means a value of T may be moved to another thread.
  • T: Sync means &T may be shared between threads.

Non-thread-safe types opt out, and spawn requires Send:

use std::rc::Rc;
use std::thread;

fn main() {
    let rc = Rc::new(5);                            // non-atomic refcount
    thread::spawn(move || println!("{rc}"));        // error[E0277]: `Rc<i32>` cannot be sent between threads safely
}

Rc uses a plain integer counter, which would race, so it is not Send; Arc is. Likewise RefCell is not Sync; Mutex is.

Scoped threads: borrowing across threads

thread::scope guarantees all threads finish before it returns, so they may borrow local data safely:

use std::thread;

fn main() {
    let v = vec![1, 2, 3, 4, 5, 6];
    let (a, b) = v.split_at(3);
    let (x, y) = thread::scope(|s| {
        let h1 = s.spawn(|| a.iter().sum::<i32>());
        let h2 = s.spawn(|| b.iter().sum::<i32>());
        (h1.join().unwrap(), h2.join().unwrap())
    });
    println!("{x} {y}");                            // 6 15
}

Atomics

For a single shared integer, an atomic is lighter than a mutex. The orderings are the same as C11’s memory_order:

use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

static HITS: AtomicUsize = AtomicUsize::new(0);

fn main() {

        for _ in 0..4 {
            s.spawn(|| {
                for _ in 0..1000 {
                    HITS.fetch_add(1, Ordering::Relaxed);
                }
            });
        }
    });
    println!("{}", HITS.load(Ordering::SeqCst));    // 4000
}

Channels: message passing

Instead of sharing memory, send values between threads. Sending moves the value, so the sender cannot keep using it:

use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();               // multiple producers, one consumer
    for id in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(id * 10).unwrap();
        });
    }
    drop(tx);                                      // close our own sender, or the loop never ends

    let mut got: Vec<i32> = rx.iter().collect();   // ends when all senders are gone
    got.sort();
    println!("{got:?}");                           // [0, 10, 20]
}

Under the hood

  • thread::spawn creates an OS thread (pthread_create on Linux). There is no green-thread runtime in std; async runtimes are separate libraries.
  • A Mutex is a futex or pthread mutex plus a poisoned flag, which is set if a thread panics while holding the lock (lock() then returns an Err).
  • Send and Sync have no runtime representation. They are checked at compile time and prevent most data races. They do not prevent deadlocks or logical races such as lock-order inversion.
  • Arc bumps its counter with an atomic add on clone and drops the value when the last owner goes away; Rc does the same non-atomically and is cheaper.

C habits to unlearn

  • Do not share a global and “remember” to lock it. Put it inside a Mutex.
  • Do not use Relaxed ordering unless you can explain it.
  • Do not hold a guard longer than needed; scope it with a block.
  • Prefer channels or scoped threads over Arc<Mutex<_>> when the data flow allows.

no_std and embedded Rust

In C

On a microcontroller you compile freestanding: no OS, no malloc unless you provide one, a startup file and a linker script that set up the stack and .data/.bss, and registers accessed through volatile pointers.

#define GPIOA_ODR (*(volatile uint32_t *)0x48000014u)

void led_on(void) { GPIOA_ODR |= (1u << 5); }

int main(void) {            /* called by Reset_Handler after startup code */
    for (;;) { led_on(); }
}

#![no_std]
#![no_main]

use core::panic::PanicInfo;
use cortex_m_rt::entry;

fn panic(_info: &PanicInfo) -> ! {      // required: what to do on panic
    loop {}                              // or reset, or log and halt
}

#[entry]
fn main() -> ! {                         // never returns, like `for (;;)` in C
    loop {}
}

Build for the target with rustup target add thumbv7em-none-eabihf and cargo build --release --target thumbv7em-none-eabihf.

Memory-mapped registers: volatile

C marks the pointer volatile. Rust has no volatile type qualifier; instead you call read_volatile and write_volatile, which are never optimized away or reordered relative to each other:

use core::ptr::{read_volatile, write_volatile};

fn main() {
    let mut reg: u32 = 0;                        // stand-in for a hardware register
    let p = &mut reg as *mut u32;
    unsafe {
        write_volatile(p, 1 << 5);               // like  REG = (1u << 5)
        let v = read_volatile(p);                // like  v = REG
        println!("{v:#x}");                      // 0x20
    }
}

On real hardware the address comes from the datasheet. In practice you rarely write this by hand: svd2rust generates a peripheral access crate (PAC) from the vendor’s SVD file, with typed register fields, and a HAL crate built on the embedded-hal traits provides drivers (GPIO, SPI, I2C, UART) that work across chips.

// with a PAC/HAL: the bit position and register name are checked by the compiler
let dp = pac::Peripherals::take().unwrap();    // ownership of ALL peripherals, once
dp.GPIOA.odr().modify(|_, w| w.odr5().set_bit());

Peripherals::take() returns the peripherals once; a second call gives None. Ownership turns “two pieces of code configure the same pin” into a compile-time error, which a C driver cannot enforce.

Heap-free data structures

Without an allocator you use fixed capacity. A buffer type with a compile-time size replaces the static uint8_t buf[N] + len pair:

fn main() {
    let mut buf = [0u8; 8];                      // fixed capacity, on the stack
    let mut len = 0;
    for b in b"hey" {
        buf[len] = *b;
        len += 1;
    }
    println!("{:?}", &buf[..len]);               // [104, 101, 121]
}

The heapless crate provides Vec<T, N>, String<N> and queues with a const capacity, and push returns a Result when full.

Shared state with interrupts

A global modified by an interrupt handler is static mut territory. Use a critical section (critical_section::with from the critical-section crate, or the older cortex_m::interrupt::free) and a critical_section::Mutex<RefCell<T>>, or an atomic for simple flags:

use core::sync::atomic::{AtomicBool, Ordering};

static DATA_READY: AtomicBool = AtomicBool::new(false);   // set in an ISR, polled in main

fn main() {
    DATA_READY.store(true, Ordering::Release);
    if DATA_READY.load(Ordering::Acquire) {
        println!("ready");
    }
}

Under the hood

  • A no_std build has no hidden runtime: no atexit, no stack unwinding if you set panic = "abort", no allocator. Code size is comparable to C when you enable opt-level = "s"/"z", LTO and codegen-units = 1.
  • core formatting (write!) is available but pulls in code; defmt encodes log strings off-target to keep flash small.
  • Generics monomorphize, so a HAL driver specialized to one pin type compiles to the same register writes as hand-written C.
  • Bounds checks remain in release builds. They are cheap, can often be removed with iterators, and can be avoided with get_unchecked in unsafe only when measured.

C habits to unlearn

  • Do not scatter volatile pointer casts; centralize register access in one module or a PAC.
  • Do not use static mut globals shared with interrupts without a critical section.
  • Do not assume malloc; decide whether the target gets alloc at all.
  • Do not write the same register-masking code in every driver; use typed fields.

    len: usize,

impl<const N: usize> RingBuffer<N> {
    fn new() -> Self {
        RingBuffer { buf: [0; N], head: 0, len: 0 }
    }

    fn push(&mut self, b: u8) -> Result<(), u8> {
        if self.len == N {
            return Err(b);                    // full: give the byte back
        }
        self.buf[(self.head + self.len) % N] = b;
        self.len += 1;
        Ok(())
    }

    fn pop(&mut self) -> Option<u8> {
        if self.len == 0 {
            return None;
        }
        let b = self.buf[self.head];
        self.head = (self.head + 1) % N;
        self.len -= 1;
        Some(b)
    }
}

fn main() {
    let mut r = RingBuffer::<2>::new();
    println!("{:?} {:?} {:?}", r.push(1), r.push(2), r.push(3));   // Ok(()) Ok(()) Err(3)
    println!("{:?} {:?} {:?}", r.pop(), r.pop(), r.pop());         // Some(1) Some(2) None
}

It uses only core types, so the same code compiles in a #![no_std] crate. The buffer’s size is a type parameter, so no allocation is needed.

In C

Recoverable errors are return codes, fatal ones call abort() or exit(), and some programs use setjmp/longjmp. Tests are a separate harness; diagnostics come from -Wall, sanitizers, Valgrind and clang-tidy.

In Rust

Two kinds of failure, kept apart:

Panics

A panic prints a message and by default unwinds: it runs Drop for live locals (chapter 11) and ends the thread. In main, that ends the program with exit code 101.

fn main() {
    let v = vec![1, 2, 3];
    let i = 7;
    println!("about to fail");
    println!("{}", v[i]);       // panics: index out of bounds: the len is 3 but the index is 7
}

Set RUST_BACKTRACE=1 to see the stack. unwrap(), expect(), assert!, unreachable!() and integer overflow in debug builds are all panics.

A panic is not an exception to catch for control flow, but catch_unwind can stop one at a boundary (a thread pool, an FFI entry):

use std::panic;

fn main() {
    let r = panic::catch_unwind(|| {
        let v = vec![1];
        v[5]
    });
    println!("{}", r.is_err());     // true
}

To make panics abort immediately (smaller binaries, no unwinding tables, and what embedded targets usually want), put this in Cargo.toml:

[profile.release]
panic = "abort"

Under the hood

  • Unwinding uses the same tables as C++ exceptions (.eh_frame), which is why panic = "abort" shrinks the binary.
  • Test functions are collected by the compiler and run by a generated harness; no registration code is needed.
  • Result-based error handling has no unwinding cost on the success path: it is a branch on a returned tag.
  • Overflow checks and bounds checks are the debug-mode “sanitizers” that C programmers add with -fsanitize=undefined; they are on by default.

C habits to unlearn

  • Do not exit() from deep inside a library. Return an error and let main decide.
  • Do not use assert for input validation (it vanishes with NDEBUG); validate and return Result.
  • Do not skip clippy; it catches C-isms such as manual index loops.
  • Do not write a separate test harness; use #[test].

Part 1: the linked list

The C version

struct node { int val; struct node *next; };
struct list { struct node *head; size_t len; };

void list_init(struct list *l);
int  list_push(struct list *l, int val);          /* -1 on malloc failure */
int  list_pop(struct list *l, int *out);          /* -1 if empty */
void list_reverse(struct list *l);
void list_free(struct list *l);                   /* caller must remember */

Review the hazards before porting: malloc can fail and the caller must check; pop uses an out-parameter and a sentinel return; nothing stops using the list after list_free; and forgetting list_free leaks.

Step 1: data layout (chapters 6, 10, 14)

A next pointer that may be NULL is Option; an owned heap node is Box:

type Link = Option<Box<Node>>;

struct Node {
    val: i32,
    next: Link,
}

pub struct List {
    head: Link,
    len: usize,
}

Option<Box<Node>> is the same size as a pointer (chapter 14), so the layout is the same as the C struct. There is no malloc failure to check: allocation failure aborts the process, which is the usual choice outside embedded code.

Step 2: construction and push (chapters 7, 13)

impl List {
    pub fn new() -> Self {
        List { head: None, len: 0 }
    }

    pub fn push(&mut self, val: i32) {
        let node = Box::new(Node { val, next: self.head.take() });
        self.head = Some(node);
        self.len += 1;
    }
}

list_init becomes new. push cannot fail, so it returns nothing. The key operation is self.head.take(): it moves the old head out and leaves None behind. In C you would write n->next = l->head; and briefly have two pointers to the same node. Rust does not allow two owners, so take() makes the hand-over explicit.

Step 3: pop and peek (chapters 8, 14)

pub fn pop(&mut self) -> Option<i32> {
    self.head.take().map(|n| {
        self.head = n.next;       // move the rest of the list up
        self.len -= 1;
        n.val
    })                            // the node's Box is freed here
}

pub fn peek(&self) -> Option<&i32> {
    self.head.as_ref().map(|n| &n.val)
}

The out-parameter and -1 are gone: Option<i32> says “a value or nothing”. free(n) is gone too, because the Box is dropped at the end of the closure. peek returns a reference tied to &self (chapter 9), so the list cannot be modified while the reference is alive.

Step 4: reverse (chapters 5, 7)

pub fn reverse(&mut self) {
    let mut prev: Link = None;
    let mut cur = self.head.take();
    while let Some(mut n) = cur {
        cur = n.next.take();      // C: next = cur->next
        n.next = prev;            // C: cur->next = prev
        prev = Some(n);           // C: prev = cur
    }
    self.head = prev;
}

It is line for line the C algorithm, with each pointer assignment written as a move. Ownership of every node passes from cur to prev exactly once, so no node is lost or freed twice.

Step 5: iteration (chapters 9, 18)

A C caller walks for (n = l->head; n; n = n->next) and can break the list while doing it. The Rust version is an iterator that borrows the list:

pub struct Iter<'a> {
    next: Option<&'a Node>,
}

impl<'a> Iterator for Iter<'a> {
    type Item = &'a i32;

    fn next(&mut self) -> Option<&'a i32> {
        self.next.map(|n| {
            self.next = n.next.as_deref();
            &n.val
        })
    }
}

impl List {
    pub fn iter(&self) -> Iter<'_> {
        Iter { next: self.head.as_deref() }
    }
}

With that, sum, max, collect, filter and the rest of chapter 18 work on your list for free.

Step 6: Drop replaces list_free (chapter 11)

The compiler writes the drop code for Box and Option automatically, but it is recursive: dropping a node drops its next, and so on. A list of a million nodes would overflow the stack. This is the classic pitfall when porting a C list. Write the loop yourself:

impl Drop for List {
    fn drop(&mut self) {
        let mut cur = self.head.take();
        while let Some(mut n) = cur {
            cur = n.next.take();      // detach, so each node drops with no children
        }
    }
}

Now list_free cannot be forgotten or called twice, and use after free cannot compile.

The C original:

#include <stdio.h>
#include <stdlib.h>

struct node {
    int val;
    struct node *next;
};

struct list {
    struct node *head;
    size_t len;
};

static void list_init(struct list *l) { l->head = NULL; l->len = 0; }

static int list_push(struct list *l, int val) {
    struct node *n = malloc(sizeof *n);
    if (!n) return -1;
    n->val = val;
    n->next = l->head;
    l->head = n;
    l->len++;
    return 0;
}

/* returns 0 and stores the value, or -1 if empty */
static int list_pop(struct list *l, int *out) {
    struct node *n = l->head;
    if (!n) return -1;
    *out = n->val;
    l->head = n->next;
    free(n);
    l->len--;
    return 0;
}

static void list_reverse(struct list *l) {
    struct node *prev = NULL, *cur = l->head;
    while (cur) {
        struct node *next = cur->next;
        cur->next = prev;
        prev = cur;
        cur = next;
    }
    l->head = prev;
}

static void list_free(struct list *l) {
    int dummy;
    while (list_pop(l, &dummy) == 0) {}
}

int main(void) {
    struct list l;
    list_init(&l);
    for (int i = 1; i <= 3; i++)
        if (list_push(&l, i) != 0) return 1;
    list_reverse(&l);
    int v;
    while (list_pop(&l, &v) == 0) printf("%d ", v);
    printf("\n");
    list_free(&l);
    return 0;
}

Part 2: the word-frequency tool

In C this needs a hash function, a table with collision handling, resizing, and string ownership: often 150 lines and several memory bugs. In Rust the standard library does it:

use std::collections::HashMap;
use std::io::{self, BufRead};

fn main() -> io::Result<()> {
    let mut counts: HashMap<String, usize> = HashMap::new();
    for line in io::stdin().lock().lines() {
        let line = line?;
        for w in line.split_whitespace() {
            *counts.entry(w.to_lowercase()).or_insert(0) += 1;
        }
    }
    let mut items: Vec<(String, usize)> = counts.into_iter().collect();
    items.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(&b.0)));   // count desc, then word
    for (w, n) in items.iter().take(10) {
        println!("{n:>6} {w}");
    }
    Ok(())
}

Put it in src/main.rs of a binary crate and run it as cargo run < somefile.txt. (Run on the Playground, it reads an empty input and prints nothing.) This uses almost every earlier chapter: HashMap and iterators (18), closures (17), String and &str (10), Result and ? (14), main returning an error (14), and tuples (6). There is no unsafe, no free and no buffer-length bookkeeping.

What stays UB inside unsafe

An unsafe block lets you do five extra things: dereference a raw pointer, call an unsafe function, access a static mut, read a union field, and implement an unsafe trait. The compiler then trusts you to keep these rules:

  • No references that are null, dangling or misaligned.
  • No &mut that aliases another live reference to the same data.
  • No data races.
  • No invalid values: a bool other than 0 or 1, an invalid char, an enum discriminant that does not exist, or uninitialized memory where an initialized value is required.
  • No out-of-bounds or misaligned pointer access, and no reads from freed memory.
  • & and &mut to a static mut are rejected by default in edition 2024 (the static_mut_refs lint). Use &raw or addr_of! to take a raw pointer instead.

Breaking any of these is UB, just as in C. The difference is scope: in C, every line may hide a violation, and in Rust only the unsafe blocks can. Keep them small, and put a // SAFETY: comment on each one that states why the rules hold.

Finding UB that remains

  • Miri interprets your program and reports UB such as out-of-bounds access, use after free, invalid values and data races, for the code paths your tests run. It needs a nightly toolchain: cargo +nightly miri test (chapter 24).
  • Sanitizers work on Rust too: AddressSanitizer and ThreadSanitizer, also on nightly.
  • cargo clippy warns about common unsafe mistakes.

Neither tool proves the absence of UB. They find what your tests reach.
