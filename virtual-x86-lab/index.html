Virtual x86 Lab - User Manual


Virtual x86 Lab is a small 32-bit x86 board that runs in your browser: an editor, an Intel-syntax assembler that writes real IA-32 machine code, a C compiler, a debugger, a serial terminal and a simulated PC-style BIOS with ACPI tables. It is a teaching tool, not a PC emulator: Datasheet 1.1 says exactly what is modelled and what is not. It shares its source with Virtual ARM Lab, which is why the editor, the Project panel and the debugger work the same way.


1. Your first five minutes


1. In the Project panel open x86/hello.s (or choose it from Open an example in the toolbar). 2. Press Build (Ctrl+B). 3. Press Run (F5). The Terminal tab prints the text the program writes to the serial port. 4. Open x86/hello.c, build and run it: the LEDs on the board count while the terminal prints. 5. Open x86/acpi.s: it finds the ACPI tables in the BIOS window and walks them, like an operating system at start-up (Datasheet 1.4).


2. The screen


The Project panel lists the files; the editor shows the open file and marks the line the CPU is on; the Board panel shows the LEDs, buttons, buzzer and the other peripherals (Datasheet 2). Tabs show the Registers (EAX to EDI, EIP and the flags; double-click one to edit it), the Memory, the Disassembly (real addresses next to your source lines) and the Terminal (the serial port at I/O 0x3F8).


3. Projects and files


Your files are kept in the browser and restored when you come back. Create a file with the + in the Project panel; a folder is part of the name (mine/test.s). Example files that you have not changed are updated when a new version of the page brings a better one; a file you have edited is never replaced. Ctrl+S saves the open file to your computer, and the project can be downloaded as project.json and opened again. A share link packs the project into a web address.


4. Writing a program


Start every program with #pragma core "x86-simple". Assembly is Intel syntax, destination first; the entry point is the label _start (or the first instruction). C files use the same line and a main. Details, the instruction list and the C rules are in Datasheet 1.2 and 1.6. The samples , , , ,  and  are the best starting points.


5. Building, running and debugging


Build (Ctrl+B) assembles or compiles the project; an error names the file and line. Run (F5) runs until the program halts (hlt), a breakpoint is hit or you press Pause; Reset (Shift+F5) starts again. Click a line number or press F9 for a breakpoint (it can have a condition). Step Into (F11) runs one instruction, Step Over (F10) runs a whole call, Step Out (Shift+F11) runs to the return. In C programs the Watch and Locals windows show the variables and the call stack. A fault (a bad address, an instruction that is not modelled) stops the CPU with a message at the line, as a triple fault would.


6. Using the board


6.1 The board and the core


The Board list in the Board panel's header shows the one board of this page, x86-simple. A program may also name it with #pragma core "x86-simple". Boards with Arm cores (Cortex-M3, M33, M7, A55), linker files and the VxWorks style kernel are in Virtual ARM Lab, a separate page.


The board's LEDs, buttons, ADC, UART, watchdog and the other peripherals are at 0x40010000; the register list is in Datasheet 2. Click the buttons on the board to give the program input.

Virtual x86 Lab - Datasheet


1. The x86-simple board (32-bit x86 with ACPI tables)


Choose it with the Board list or #pragma core "x86-simple" in an assembly file (User Manual 6.1). It is not an Arm core: it is a small Intel-style board for learning how a PC-class system finds its hardware, built around one sample () that finds the ACPI tables and walks them. It is a teaching model written from the author's memory of the IA-32 and ACPI documents; nothing here was checked against Intel's manuals or the ACPI specification, so every table layout, port number and register behaviour below is this emulator's own. Programs are IA-32 assembly or C: the C compiler's output is translated into IA-32 code, and the board has the same LEDs, buttons, ADC, timer, UART, I²C and SPI as the Cortex boards, at the same addresses (1.6).


1.1 What is modelled and what is not




ItemHere


Mode32-bit protected mode with a fixed flat memory model: no segments to set up, no paging, no privilege levels, no real mode, no 16-bit code (the 0x66 prefix selects 16-bit operands only)


RegistersEAX ECX EDX EBX ESP EBP ESI EDI (with AX/AL/AH style parts), EIP, and the flags CF PF ZF SF OF IF (DF exists in EFLAGS but there are no string instructions). AF is not kept. Reset: ESP = 0x1FFFF0, EIP = the entry label, all other registers 0, IF = 0


Not modelledinterrupts and exceptions (the IDT, INT, IRET: any fault stops the CPU with a message, like a triple fault), segment registers, control registers, paging, string instructions (MOVS, REP), XCHG, BT, SETcc, 8-bit and 16-bit MUL/DIV, RCL/RCR, 16-bit IMUL, the three-operand IMUL, PUSHA/POPA, PUSHF/POPF, the FPU and SIMD, 64-bit mode, cache and timing (1 instruction = 1 µs), SMP, the APIC, PIC, PIT, HPET, PCI, CMOS and the keyboard controller


Self-modifying codethe interpreter decodes the bytes in memory, so code that changes its own bytes runs as changed. The debugger still maps EIP to the instruction records made at Build, so a jump to an address that is not the start of one of them stops with a message




1.2 The assembler and the instructions


The assembler is Intel syntax (destination first), case-insensitive for instructions and registers, case-sensitive for labels. It writes real IA-32 machine code (opcode, ModRM, SIB, displacement, immediate, the 0x66 prefix for 16-bit operands) and chooses the short or long form of jumps itself; the Disassembly window shows the addresses (the program starts at 0x00100000) next to your source lines.




ItemSyntax


InstructionsMOV MOVZX MOVSX LEA PUSH POP ADD ADC SUB SBB AND OR XOR CMP TEST INC DEC NEG NOT SHL (SAL) SHR SAR ROL ROR IMUL MUL DIV IDIV CDQ BSR BSWAP CMC CLC STC JMP Jcc CALL RET IN OUT HLT NOP CLI STI. IMUL has the two-operand form (imul eax, ebx) and the one-operand form (EDX:EAX = EAX * the operand); MUL, DIV and IDIV are 32-bit (EDX:EAX divided by the operand; division by zero or a quotient that does not fit stops the CPU as a divide error). Jcc: JO JNO JB (JC JNAE) JAE (JNC JNB) JE (JZ) JNE (JNZ) JBE (JNA) JA (JNBE) JS JNS JP (JPE) JNP (JPO) JL (JNGE) JGE (JNL) JLE (JNG) JG (JNLE). PUSH and POP take 32-bit registers (PUSH also an immediate or a dword in memory)


Operandsregisters (eax, ax, al...), immediates (an expression), memory [base + index*scale + displacement] with byte, word or dword ptr in front when no register gives the size (mov byte ptr [ebx], 7). Both operands of an instruction cannot be memory. offset label is the same as label


Expressionsnumbers (10, 0x1F, 0b101), characters 'A', labels, NAME equ value constants, $ (the address of the current line), and + - * / % << >> & | ^ ~ with parentheses


Directivesdb dw dd (also .byte .word .short .long .int; numbers and "strings"), .ascii .asciz .string, .space n[, fill], times n db ..., .org address (not backwards), .align n, NAME equ value or .equ NAME, value. bits 32, .intel_syntax noprefix, section, global and similar lines are accepted and ignored. Comments start with ; (or //)


Entrythe label _start, else start, else main, else the first instruction


FlagsADD/ADC/SUB/SBB/CMP set CF OF SF ZF PF; AND/OR/XOR/TEST clear CF and OF; INC/DEC leave CF alone; a shift by 0 changes nothing; the hardware defines OF after a shift only for a count of 1, and this emulator computes it the same way for any count; NEG sets CF unless the operand was 0; NOT and MOV change no flags

1.4 The ACPI tables and the power-management block


At every reset the board puts these tables into the BIOS window, as firmware does on a PC. Layouts follow the structure of the ACPI tables as remembered (header, RSDP v2, XSDT, FADT, MADT, DSDT); the table contents, OEM names and addresses are this emulator's own, and AML is not interpreted: the DSDT holds two hand-encoded AML objects that a program can find by scanning for their names.




AddressTableContents


0xE0200a decoythe text RSD PTR  with a wrong checksum: a program must verify the checksum, as a real OS does, and skip it


0xE0F40RSDP (v2, 36 bytes)signature "RSD PTR " at +0, checksum of the first 20 bytes at +8, OEM id "VARLAB", revision 2 at +15, RSDT address 0 at +16 (no RSDT), length 36 at +20, XSDT address at +24, checksum of all 36 bytes at +32. On a 16-byte boundary


0xE1000XSDT36-byte header (signature, length at +4, revision, checksum at +9 so the whole table sums to 0, OEM fields), then 8-byte table addresses: the FADT, the MADT


0xE1100FADT ("FACP", 244 bytes, revision 3)DSDT address at +40, PM1a_EVT_BLK +56 = 0x600, PM1a_CNT_BLK +64 = 0x604, PM_TMR_BLK +76 = 0x608, PM1_EVT_LEN +88 = 4, PM1_CNT_LEN +89 = 2, PM_TMR_LEN +91 = 4, X_DSDT +140 and the 12-byte generic address structures X_PM1a_EVT_BLK +148, X_PM1a_CNT_BLK +172, X_PM_TMR_BLK +208 (system I/O). Everything else is 0 (no SMI command port, no FACS, no reset register)


0xE1200MADT ("APIC", 52 bytes)local APIC address 0xFEE00000 at +36, flags 1 at +40, then one Processor Local APIC entry at +44 (type 0, length 8, processor id 0, APIC id 0, flags 1 = enabled). There is no APIC: the table only says how many processors there are


0xE1300DSDT (revision 2)AML bytes 08 5F 53 35 5F 12 08 04 0A 05 0A 05 00 00 = Name(_S5_, Package(){5, 5, 0, 0}) (the sleep type of the soft-off state S5 is 5) and 5B 82 0B 44 45 56 30 08 5F 55 49 44 00 = Device(DEV0){Name(_UID, 0)}. A program finds SLP_TYP by scanning for _S5_: the byte after it is 0x12 (PackageOp), then come the package length, the element count and 0x0A (BytePrefix), and the byte at +8 from the name is the first element, SLP_TYPa






PortRegisterBehaviour


0x600 (16 bits)PM1_STSreads 0; a write of 1s clears bits (nothing sets them)


0x602 (16 bits)PM1_ENstores what was written; there are no interrupts, so it has no effect


0x604 (16 bits)PM1a_CNTbit 0 SCI_EN (1 after reset), SLP_TYP in bits 12:10, SLP_EN in bit 13. Writing SLP_EN with SLP_TYP equal to the value in _S5_ (5) powers the board off: the run stops with "Powered off: ACPI S5". Other sleep types are logged and ignored (S1-S4 are not modelled). Only word or dword writes count; byte writes are ignored


0x608 (32 bits)PM_TMRa 24-bit counter at 3.579545 MHz, taken from the cycle count (1 µs per instruction), so it advances 3.58 ticks per instruction




Configuring the tables. The project file x86/acpi.cfg (in the Project panel, next to acpi.s) changes them. Edit it and press Build; the tables are rebuilt at every reset. If the project has no file named acpi.cfg, the defaults in the table above are used. One setting per line, ; or # starts a comment:




LineEffect


cpus NN (1 to 8) enabled Processor Local APIC entries in the MADT; the table grows by 8 bytes per processor


s5 Nthe SLP_TYP value (0 to 7) in the _S5_ package of the DSDT; writing that value with SLP_EN to PM1a_CNT powers off


oem TEXTthe OEM id (1 to 6 characters) in the RSDP and every table header

A mistake is a build error that names the line of acpi.cfg. The checksums are always recomputed. The port addresses and the table placement cannot be changed. Try cpus 4 and run acpi.s: it reports 4 enabled processors.


1.6 C programs and the board's peripherals


A file with #pragma core "x86-simple" may be C. The C compiler is the one of the Cortex-M3 (the same language, structs, bit-fields, 64-bit integers, float and double through the soft-float library); its Thumb output is translated line by line into IA-32 code, as it is for the Cortex-A55. main is called after the global data is set up; when it returns the CPU halts (HLT). Bare-metal C has no printf (as on the Cortex-M3): use uart_puts, uart_putc and your own number printing. There are no interrupts: write loops that poll, as in the samples. A line that uses a Cortex-M system register or instruction (MRS, MSR, SCB_CPUID, the NVIC, SysTick) is refused or faults, because this core has none.




ItemHow it is done (this emulator's own ABI, not cdecl)


RegistersIA-32 has eight registers; the compiler's r0-r12 live in memory at 0x1000 + 4n. Every compiler instruction loads its operands into EAX/ECX/EDX, computes, and stores the result back, so the code is about three times as long and slower than hand-written IA-32. sp is ESP, r11 is the frame pointer


Callsarguments in r0-r3 (further ones on the stack), the result in r0 (r0:r1 for 64 bits), r4-r11 saved by the callee. A call is the call instruction, which pushes the return address where the Cortex-M code keeps lr, so a function starts by pushing r4-r11 and ends by popping them and ret; the frame is laid out as on the Cortex-M3. Assembly that calls C, or is called from C, must follow this: put the arguments in the words at 0x1000, 0x1004, 0x1008, 0x100C and read the result at 0x1000


Flagsafter a subtraction or compare the IA-32 carry is a borrow, where the Arm C is not; the translation inserts cmc where an adc or sbb follows the other kind of instruction. Division by zero gives 0 (and INT_MIN / -1 gives INT_MIN) as on the Cortex-M3, it does not stop the CPU


GPIO0x40010000 GPIO_DIR (1 = output), 0x40010004 GPIO_OUT, 0x40010008 GPIO_IN (buttons read 1 while pressed): P0-P7 are the LEDs and buttons of the board panel


UART0x40011000 UART_TX, 0x40011004 UART_STATUS (bit 0 = ready to send, bit 1 = a character received), 0x40011008 UART_RX: the Terminal tab, as COM1 at I/O 0x3F8 is


Timer, ADC, I²C, SPI, watchdogat the addresses of the Cortex-M3 (0x40012000 timer, 0x40013000 I²C, 0x40014000 SPI, 0x40016000 ADC, 0x40017000 watchdog; Datasheet 5); the C names (TIM_COUNT, ADC_CTRL, delay_us(), ...) work as on the Cortex-M3. The timer counts executed instructions (1 per µs), so a C program on this board runs about three times slower in board time than the same program on the Cortex-M3


Not presentthe NVIC and every interrupt (there is no IDT), SysTick, the Cortex system registers (0xE000xxxx), the MPU, the messaging unit and the soft-float helper registers beyond the library; a read or write there stops the CPU with "access to unmapped memory"




#pragma core "x86-simple"
int main(void)
{
    GPIO_DIR = 0xFF;                        /* P0-P7 are outputs */
    GPIO_OUT = 0x2A;                        /* LEDs P1, P3 and P5 light up */
    uart_puts("LEDs set from C on x86-simple\n");
    return 0;                               /* main returns: the CPU halts */
}

1.5 Debugging


Build, Run, Step Into, Step Over (a call runs to its return), Step Out, breakpoints on lines and the Memory, Disassembly and Registers windows work as on the other cores. The Registers window shows EAX-EDI, EIP, the flags, EFLAGS, the PM timer and PM1a_CNT, and for a C program also R0-R12, the compiler's virtual registers. Breakpoints, Step Over and Step Into work on the C lines, Locals and Watch read variables through the frame pointer r11. The Memory window reads the board's memory and shows nothing for unmapped addresses. A run ends with one of: Halted: HLT (there are no interrupts to wake the CPU, so HLT stops it for good), Powered off: ACPI S5, or Fault with the cause and the source line (unmapped access, running into data, jumping into the middle of an instruction, unknown opcode). Try  first:


#pragma core "x86-simple"
_start: mov esi, msg            ; esi = the address of the text
next:   mov al, [esi]           ; one character
        test al, al             ; the text ends with a zero byte
        jz done
        mov edx, 0x3F8          ; ports above 255 need the port number in dx
        out dx, al              ; COM1: the character appears in the Terminal tab
        inc esi
        jmp next
done:   hlt                     ; stop the CPU
msg:    db "Hello from x86-simple", 10, 0


The sample  then does what an operating system does at start-up: it scans 0xE0000-0xFFFFF for the RSDP and rejects the decoy by its checksum, follows the XSDT to the FADT and the MADT, counts the processors, reads the power-management ports, finds _S5_ in the DSDT, reads the PM timer twice and writes SLP_TYP and SLP_EN to PM1a_CNT. Its output is the list of tables with their addresses and lengths and ends with "powering off".


2. Peripheral registers


All registers are 32 bits wide; unused bits read 0. Access: R = read, W = write, RW = both.

if (GPIO_IN & 0x10) { ... }      /* SW4 is pressed */



2.2 UART (base 0x40011000)




OffsetC nameAccessDescription


0x0UART_TXWWriting sends bits 7-0 to the terminal. Transmission is instant.


0x4UART_STATUSRBit 0: TX ready (always 1). Bit 1: at least one received byte is waiting.


0x8UART_RXRReading returns the oldest received byte and removes it (0 if none is waiting). Bytes come from the Terminal input box.




Interrupt source 1 is pending while a received byte is waiting.



2.3 Timer (base 0x40012000)




OffsetC nameAccessDescription


0x0TIM_COUNTRWFree-running counter of cycles (µs) since reset; it always counts, even when the timer is disabled. Writing sets the count.


0x4TIM_LOADRWPeriod in µs.


0x8TIM_CTRLRWBit 0: enable. Every write starts a new period of LOAD µs from now.


0xCTIM_FLAGRWReads 1 when the timer is enabled, LOAD > 0 and the period has elapsed. Any write clears it and starts the next period (one LOAD after the end of the previous one, so a periodic timer does not drift).




Interrupt source 0 is pending while FLAG reads 1, so a timer handler must write TIM_FLAG.


TIM_LOAD = 1000;                 /* 1 ms period */
TIM_CTRL = 1;                    /* start */
while (!TIM_FLAG) { }            /* wait 1 ms */
TIM_FLAG = 0;                    /* next period */



2.4 I²C master (base 0x40013000)




OffsetC nameAccessDescription


0x0I2C_ADDRRWBits 6-0: 7-bit address of the device.


0x4I2C_DATARWBits 7-0: the byte to write, or the byte read.


0x8I2C_CTRLW1 = write DATA to the device. 2 = read a byte from the device into DATA. Add 4 (bit 2, STOP) to end the transfer after this byte; 4 alone just sends a STOP. Each byte completes at once.


0xCI2C_STATUSRBit 0: ACK, 1 if a device answered the last transfer.




Temperature sensor at 0x48. A write sets its register pointer to DATA. A read returns the register the pointer selects: register 0 is the temperature in °C (0-99, set with the slider on the board); other registers read 0. Without a device at the address, STATUS bit 0 is 0 (NACK) and a read gives 0xFF.


I2C_ADDR = 0x48;
I2C_DATA = 0;  I2C_CTRL = 1;     /* select register 0 */
I2C_CTRL = 2;                    /* read it */
if (I2C_STATUS & 1)
  temp = I2C_DATA;               /* degrees C */


Transfers. A transfer starts with the first byte after a STOP, after a change of I2C_ADDR, or with a write that follows a read (a repeated start). It ends with STOP. The temperature sensor treats every write as a new register pointer, so it works with or without STOP.


EEPROM at 0x50 (like a 24C02): 256 bytes, 0xFF when erased, kept across Reset, Build and page reloads (in your browser; Clear EEPROM on the board erases it).


    

  • Write: the first byte of a write transfer is the memory address; the following bytes are data, at most one 8-byte page (a write past the end of the page wraps to the start of the same page, as on real chips). The bytes are stored at the STOP; bytes never ended with a STOP are dropped when the next transfer starts.
    • 

  • Write cycle: after the STOP the chip stores the data for 5 ms and does not answer (NACK) meanwhile. Wait by sending its address until it answers ("acknowledge polling").
    • 

  • Read: write the memory address (no STOP), then read bytes; the address counts up after each byte, across pages. End the last read with STOP.
    • 



I2C_ADDR = 0x50;                                   /* store 0x12 0x34 at 16 */
I2C_DATA = 16;   I2C_CTRL = 1;                     /* memory address */
I2C_DATA = 0x12; I2C_CTRL = 1;
I2C_DATA = 0x34; I2C_CTRL = 1 | 4;                 /* last byte + STOP */
do { I2C_DATA = 0; I2C_CTRL = 1 | 4; } while (!(I2C_STATUS & 1));   /* wait 5 ms */
I2C_DATA = 16;   I2C_CTRL = 1;                     /* read it back */
I2C_CTRL = 2;     a = I2C_DATA;
I2C_CTRL = 2 | 4; b = I2C_DATA;



2.5 SPI master (base 0x40014000)




OffsetC nameAccessDescription


0x0SPI_DATARWWriting sends bits 7-0 on MOSI to the 8-bit shift register, whose lights show the byte. At the same time a byte is received on MISO; reading SPI_DATA returns it.


0x4SPI_STATUSRBit 0: transfer done (always 1; transfers are instant).




The byte received is the next one from the board's MISO input box (the list repeats). The box takes hex digits two at a time: A5 3C, A53C and 0xA53C are the same two bytes and 12345 is 12 34 05. If the box is empty, the device returns the byte sent before (loopback).



2.6 ADC (base 0x40016000)




OffsetC nameAccessDescription


0x0ADC_CTRLRWBits 1-0: channel. Writing with bit 4 set starts a conversion of that channel.


0x4ADC_STATUSRBit 0: done (a result is waiting). Bit 1: busy.


0x8ADC_DATARThe 12-bit result, 0-4095 for 0-3.3 V. Reading it clears "done".

A conversion takes 10 µs; the value is taken at its end. Interrupt source 5 is pending while "done" is set, so a handler reads ADC_DATA. Result to millivolts: mV = raw * 3300 / 4095.


ADC_CTRL = 0 | 0x10;             /* channel 0, start */
while (!(ADC_STATUS & 1)) { }    /* about 10 us */

2.7 Watchdog (base 0x40017000)


The watchdog resets the CPU when a program stops working: once started, the program must kick it before the timeout, or the whole CPU is reset. It is off after every reset, so only a program that starts it is affected.




OffsetC nameAccessDescription


0x00WDT_CTRLRWBit 0: enable. Bit 1: early-warning interrupt. Bit 2: lock. A write counts only with the key 0x5A in bits 31-24 (for example 0x5A000001); other writes are ignored, so a stray write cannot start or stop it. Starting it starts a full timeout. Once locked, it cannot be stopped or unlocked until the next reset.


0x04WDT_RELOADRWTimeout in µs, 1 to 16,777,215 (about 16.7 s); 1,000,000 after reset. Used at the next start or kick.


0x08WDT_KICKWWrite 0xAAAA to start the timeout again. Other values do nothing.


0x0CWDT_COUNTRµs left before the reset (0 when off).


0x10WDT_STATUSRWBit 0: early warning (write 1 to clear). Bit 1: running.


0x14WDT_RSTCAUSERWhy the CPU last reset: 1 power-on (Build), 2 Reset button, 3 watchdog, 4 software reset (SCB_AIRCR).




    

  • Timeout: the CPU resets as at power-on (RAM cleared, watchdog off, the program starts again), the WDT light on the board flashes red, the status bar and Output say so, and WDT_RSTCAUSE reads 3. The EEPROM and the terminal text are kept. If it happens during a step, the step stops.
    • 

  • Early warning: with bit 1 set, interrupt source 6 becomes pending once, when a quarter of the timeout is left; the handler clears it by writing 1 to WDT_STATUS bit 0 (a kick clears it too).
    • 

  • Paused CPU: the watchdog counts virtual time, so it stops whenever the CPU is paused, at a breakpoint or between steps.
    • 

  • While it runs, the WDT light is green.
    • 



WDT_RELOAD = 500000;              /* 500 ms */
WDT_CTRL = 0x5A000001;            /* key + enable */
while (1) {
  work();
  WDT_KICK = 0xAAAA;              /* "still alive" */
}
